# OS変更通知による差分インデックス

## 目的

通常検索時に登録フォルダ全体を `scandir` / `stat` するのをやめ、OSが通知した変更がある検索対象だけを再インデックスする。

## macOS

バックエンド起動中は PyObjC の FSEvents を利用する。通知を受けたファイルまたはフォルダを含む検索対象を `target_change_states.is_dirty = 1` として保存する。検索時は次の規則で動作する。

- `is_tracking = 1` かつ `is_dirty = 0`: 既存インデックスだけを検索し、走査しない。
- `is_dirty = 1`: 既存結果を優先して返し、既存の安全な差分走査をバックグラウンド実行する。
- インデックス成功時: `is_dirty = 0` に戻す。

FSEvents はイベントをディレクトリ単位に集約する場合がある。そのため現実装では、変更を含む登録対象フォルダを差分走査する。削除・移動・イベント集約時も整合性を失わないことを優先している。

検索対象フォルダの追加・削除・有効/無効の切り替えは 2 秒間隔で監視し、変化があれば FSEvents の監視を張り直す。新しく監視対象になったフォルダは dirty として一度再照合する。
起動時に検索対象が 0 件でも、監視の張り直しと dirty 対象の更新ワーカーは起動しておく（起動後に最初のフォルダを追加した場合も、再起動なしで自動更新が始まる）。

バックエンド停止中に起きた変更を取りこぼさないため、起動時は全登録対象を一度だけ dirty として再照合する。その後は変更通知がある対象だけを更新する。FSEvents/PyObjC を利用できない環境では従来の更新間隔ベースの差分走査へ安全にフォールバックする。

## Windows

Windowsランチャーの `/api/search/indexed` は既存インデックスだけを検索し、変更追跡や更新完了を待たない。更新はバックエンド内の専用ワーカーが行い、通知から2秒静まった dirty 対象を1件ずつ既存の `IndexService.ensure_fresh_target()` で安全に差分走査する。成功時には既存のインデックス完了処理が `is_dirty = 0` に戻す。

### NTFS: USN Change Journal

NTFS のローカルドライブでは USN Change Journal を第一候補にする。`windows_usn_journals` テーブルに、ボリュームルート、Journal ID、最後に処理した USN を保存する。起動時および1秒間隔の確認で保存USN以降を読み取るため、バックエンド停止中の作成・内容更新・削除・移動も次回起動後に検出できる。

- 初回監視でカーソルがない対象は安全側で dirty にし、現在の Journal ID / USN を保存する。
- Journal ID の変更、保存USNが終端より先、USNレコード破損、履歴欠落、権限・読み取りエラーでは、そのボリューム配下の有効対象を dirty にする。次の既存差分走査で整合性を回復する。
- 削除済みの USN レコードなど、ファイルIDからパスを解決できない変更も同様にボリューム単位で dirty にする。これは削除と移動を見逃さないための安全側の制約である。

`OpenFileById` で現存パスを解決できる USN レコードは対象パスまで絞り込む。アプリのDB、`-wal` / `-shm`、ログ、キャッシュ配下は共通の除外判定を通すため、自身のSQLite更新で dirty を繰り返さない。

### USN 非対応時: ReadDirectoryChangesW

FAT / exFAT、ネットワーク共有、権限不足やセキュリティポリシーにより USN を開けないドライブ（会社PC等の制限環境含む）では `ReadDirectoryChangesW` の再帰監視を開始する。監視開始不能、読み取り失敗、監視バッファ溢れ（0バイト通知）時は対象ルートを dirty にする。これにより通知を失った場合でも次の安全な差分走査で回復する。プロセス停止中の履歴は USN 非対応ファイルシステムには存在しないため、次回の監視開始・失敗検出時の再照合に依存する。

登録されている全ボリュームが `ReadDirectoryChangesW` へフォールバックされた場合、毎秒の USN ポーリングスレッドは無駄なリソース消費を防ぐため自動的に終了・停止する。また、監視追跡の開始成否に関わらず `dirty_refresh_worker` は常時起動され、手動インデックスや他の契機で dirty となった対象のバックグラウンド差分更新が保証される。

Windows API 呼び出しは `windows_change_tracking.py` の薄いラッパーに隔離している。標準ライブラリの `ctypes` のみを使い、サービス制御部は偽APIを注入できるため、非WindowsでもUSN正常、履歴欠落、フォールバック、ポーリングスレッド停止、自己更新除外をユニットテストできる。

### 運用ログ
監視ハンドルの取得、フォールバック発生、変更検出、dirty 化、バックグラウンド更新の開始/完了などのイベントを `ChangeTrackingService:` および `WindowsChangeTracker:` プレフィックスで統一的にログ出力し、実機や制限環境での動作状況の追跡を容易にしている。

macOS の FSEvents は通知の頻度が高いため、受信そのものは DEBUG、対象を dirty にしたときだけ INFO（変更パスの例つき）で記録する。
`backend/backend.log` は 10MB ごとにローテーションし、直近 5 世代だけを残す。

## 変更通知の絞り込み（macOS / Windows 共通）

通知された変更パスは、対象を dirty にする前に次の順で絞り込む（`backend/app/services/change_relevance.py`）。

1. **アプリ自身の書き込みを無視する**: データフォルダ（検索DB・`-wal` / `-shm`・設定）、`backend.log`（`backend.log.1` などローテーション済みを含む）、ランチャーのログ。
2. **検索対象フォルダの配下かどうか**: 配下にない変更は無視する。
3. **除外キーワードに該当する変更を無視する**: その検索対象の除外キーワード（`targets.exclude_keywords`。グローバル設定と自動除外パスを含む）に、
   変更パスの途中のフォルダ名・ファイル名・パス形式のいずれかが該当する場合、走査しても結果は変わらないので dirty にしない。
   判定はインデックス走査と同じ規則（`exclude_rules.py`）を使う。

3 がない場合、検索対象の中にある `.git/`、`node_modules/`、Obsidian のプラグインデータなど、
除外しているフォルダへの書き込みのたびに対象全体の差分走査とベクトル同期が走り続ける。

除外キーワードを設定から外した場合は、通知ではなく設定保存時の同期（`targets.exclude_keywords` の更新）によって次回の走査が必要と判定される。

## バックグラウンド更新とベクトル同期連動

`dirty_refresh_worker` によるバックグラウンド差分更新では、スレッドセーフな専用 DB 接続を `IndexService(connection=connection, enable_vector_sync=True)` に渡す。これにより、通常の全文検索（SQLite / FTS5）の更新と削除クリーンアップだけでなく、**ベクトルインデックス（Vector DB）の差分更新（`vector_state.sync_index`）も自動連動**して実行される。ファイル名変更（リネーム）や新規作成が発生した場合も、デフォルトのハイブリッド検索（`hybrid`）ですぐに最新状態が反映される。

バックグラウンド差分更新が失敗した対象は dirty のまま残すが、すぐには再試行しない。失敗が続くごとに待機時間を 30 秒から倍にし（上限 10 分）、成功すると解除する（`ChangeTrackingService._refresh_failures`）。待機中の対象があっても、他の dirty 対象の更新は止めない。失敗直後に全走査を 0.5 秒ごとに繰り返すと、サーバーが応答しなくなるため。

## 検索時の並行インデックス耐性 (409 Conflict 回避)

ファイル変更直後にデスクトップランチャー等から検索が行われ、バックグラウンド更新とタイミングが重複した場合、`IndexService.ensure_fresh_target()` は `HTTP 409 Conflict: Indexing is already running.` を送出する。
フォルダ未指定検索（`search_refresh.SearchRefresher.refresh_registered_targets`）では、この 409 Conflict をエラーとせず安全にキャッチして同期インデックス処理のみをスキップし、**既存インデックスを用いて即座に検索応答を返す**。これにより、ファイル名変更直後の検索であってもランチャーがフリーズ・エラー停止することなくシームレスに動作する。
