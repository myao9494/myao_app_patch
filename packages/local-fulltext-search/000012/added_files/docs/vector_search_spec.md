# ベクトル検索 & ハイブリッド検索 仕様書

## 1. 概要
本機能は、埋め込みモデル（Embedding Model）による意味・概念の類似度検索（Dense Retrieval）と、SQLite FTS5 による高速な全文キーワード検索（Sparse Retrieval）を融合したハイブリッド検索システムを提供する。
また、PoC (`PoC_lag`) の知見を活かし、Markdown 以外の全選択拡張子・全登録フォルダを対象とし、専門用語辞書（Glossary）による表記揺れ展開や、ノイズフロアカット・Dense/Lexical 複合ブーストを備える。

## 2. 検索方式と既定値

| 方式 | 識別子 (`search_type`) | 特徴 | 適用ユースケース |
| :--- | :--- | :--- | :--- |
| **ハイブリッド検索**（既定） | `hybrid` | キーワード完全一致と意味類似度を RRF ($k=60$) で合成 | 日常的な検索全般（見落とし防止と高精度順位を両立） |
| **ベクトル検索** | `vector` | 埋め込みベクトルのコサイン類似度で検索 | 言い換え、類義語、質問文、抽象的な概念検索 |
| **通常検索** | `keyword` | SQLite FTS5 による全文キーワード検索 | 特定の型番、英数字コード、完全一致テキスト検索 |

※ Web UI および API の既定値は必ず `hybrid` とする。

## 3. アーキテクチャ

```
[クライアント (Web UI / ランチャー)]
           │
           │ search(q, search_type="hybrid")
           ▼
[Search API (/api/search, /api/search/indexed)]
           │
           ▼
[search_dispatcher.dispatch_search]
           │
           ├─► search_type == "keyword" ─► [SearchService (FTS5)] ──────────────────┐
           │                                                                         │
           ├─► search_type == "vector"  ─► [VectorSearcher (FAISS)]                  │
           │                                  │ 絞り込み + files.id へ解決           │
           │                                  └──────────────────────────────────────┤
           └─► search_type == "hybrid"                                               │
                                     ┌────────────┴────────────┐                     │
                                     ▼                         ▼                     │
                            [SearchService (FTS5)]    [VectorSearcher (FAISS)]       │
                                     │                         │ 絞り込み            │
                                     └────────────┬────────────┘                     │
                                                  │ RRF 融合 (k=60)                   │
                                                  │ 一致バッジ & 核心文付与           │
                                                  │ files.id へ解決・ページ切り出し   │
                                                  ▼                                  ▼
                                        [SearchResultItem 一覧] ◄────────────────────┘
```

- 検索方式ごとの実行・絞り込み・ID 解決・ページングは `backend/app/services/search_dispatcher.py`、
  RRF の計算は `backend/app/services/hybrid_search_service.py` が担う。
- ベクトルモデルが未ロード、ベクトル検索が失敗、またはベクトル結果が 0 件のとき、hybrid はキーワード検索の結果だけを返す。

### 3.1 ベクトル結果の絞り込み

ベクトル検索の結果は、キーワード検索と同じ条件を満たすものだけを採用する（`VectorCandidateFilter`）。

- 除外キーワード（リクエスト指定が無ければ保存済みの設定）に、ファイル名・ステム・パス構成要素が該当しない。
- 拡張子フィルタ（`types` / `extensions` / `index_types`、`-png` のような除外指定を含む）に合致する。
- 検索語の `-語` がパスにもヒット本文にも含まれない。ベクトル検索へ渡すクエリは `-語` を除いたポジティブ語だけ。
- フォルダ指定があればその配下、無ければ現在有効な検索対象フォルダのいずれかの配下にある。
- ローカルファイルは実在する（削除済みファイルのゴーストを返さない）。

### 3.2 結果の `file_id`

ベクトルDBの `documents.id` と全文検索DBの `files.id` は別の ID 体系である。
`file_id` はクリック記録（`POST /api/search/click`）とファイル削除（`DELETE /api/files/{file_id}`）で `files.id` として使われるため、
ベクトル由来の結果は次の規則で `file_id` を決める。

- 同じパスの行が `files` にあれば、その `files.id` を使う。クリック数と `top` タグも `files` の値を返す。
- `files` に無い文書（全文インデックスの対象外など）は、負の合成 ID `-(1_000_000_000 + documents.id)` を使う。
  どの `files.id` とも衝突しないため、クリック記録や削除を要求しても 404 になり、別のファイルに作用しない。
- 「両方一致」の判定とこの解決は、区切り文字（`\` / `/`）と大文字小文字の違いを吸収したパス比較キーで行う
  （Windows ではベクトルDBが `\` 区切り、全文検索DBが `/` 区切りでパスを保存しているため）。

### 3.3 hybrid のページング

- 全体順位は「先頭 1 ページ分（`limit` 件）のキーワード結果とベクトル結果を RRF 融合して並べ替えた部分」に、
  残りのキーワード結果（融合部分に既に含まれるものを除く）を元の順位のまま続けたものとする。
- 各ページはこの全体順位から `offset` / `limit` で切り出す。1 ページ目は融合結果の上位 `limit` 件。
  ページをまたいでもベクトル結果が重複したり、融合で押し出されたキーワード結果が失われたりしない。
- クライアントは、応答の `next_offset` を次の要求の `offset` に、同じ `limit` で渡す。
- `total` は、キーワード検索とベクトル検索のどちらかに一致したファイルの数（重複なし）。どのページを取得しても同じ値になる。
  融合部分では「ベクトルのみ」に見える結果が、後ろのページのキーワード結果でもある場合は 1 件として数える
  （キーワード結果に続きがあるときだけ、該当ファイルに絞ったキーワード検索を 1 回追加して確認する）。
- `search_type=vector` はページングせず、上位 `limit` 件だけを返す（`has_more` は常に `false`）。

## 4. データモデルとストレージ
- **モデル配置**: `models/` ディレクトリ（例: `models/ruri-v3-30m`, `models/ruri-v3-310m`, `models/ruri-v3-70m`）。Git 管理からは除外。
- **ベクトルデータベース**: SQLite (`backend/data/vector_index_<model_name>.db`)。モデルごとに別ファイル。
  - `documents`: `path`（一意）、`title`、`mtime`、`size`、`sha256`、`text`（本文）、`embedding`（本文先頭 1000 文字の文書ベクトル）、`indexed_at`
  - `chunks`: `document_id`、`chunk_index`、`text`、`embedding`（float32 ベクトル BLOB）、`embedding_dim`。文書を削除するとチャンクも連動して削除される。
  - 前後の文脈は、同じ文書の `chunk_index ± 1` のチャンクを検索時に取得する。
- **書き込みの単位**: 1 文書とそのチャンクは 1 トランザクションで保存する（`save_document_with_chunks`）。
  途中で失敗した場合はロールバックし、「登録済みだがチャンクが無い」文書を残さない（残ると差分検知で変更なしと判定され、検索に出ないまま再作成されなくなる）。
- **接続**: 処理ごとに `open_db()` で接続を開き、必ず閉じる。インデックス作成中は 1 本の接続を使い回し、検索時は候補の本文・文脈を 1 接続でまとめて取得する。
- **FAISS インデックス**: `faiss.IndexFlatIP`（正規化済みベクトルの内積＝コサイン類似度）により、数万件〜数十万件のチャンクを数ミリ秒で高速探索。初回検索時にベクトルDBから全チャンクを読み込んでメモリ上に構築し、インデックス更新後に作り直す。

## 5. チャンキング仕様
- **Markdown ファイル**:
  - 見出し（H1〜H6）単位でのセマンティック分割。
  - フロントマター（YAML）やパンくず（`# 見出し1 > ## 見出し2`）のコンテキスト保持。
  - Obsidian wikilink (`[[リンク\|表示名]]`) の自動展開。
  - Excalidraw 描画バイナリ/JSON データの自動除去によるクリーンなテキスト抽出。
- **非 Markdown ファイル（PDF, Word, Excel, TXT, JSON, MSG 等）**:
  - 汎用テキスト抽出エンジン経由で本文を取得。
  - スライディングウィンドウチャンキング（既定 500 文字 / オーバーラップ 100 文字）。
- **画像・音声・本文なし拡張子（PNG, JPG, MP3 等）**:
  - ファイル名をテキストとして埋め込みベクトル化（例: `2026年度_予算計画書.xlsx` のファイル名から意味を捉えて類似検索可能）。

## 6. インデックス自動同期 & 差分検知仕様
- **差分検知ロジック（2段階スキップ）**:
  - 第1段階: ベクトルDB（`vector_index_<model>.db`）に記録された前回の `mtime`（最終更新日時）および `size`（ファイルサイズ）と現在の値を照合。完全一致ならテキスト抽出・Embedding計算を即座にスキップ。
  - 第2段階: `mtime` や `size` が変化していても、SHA-256 ハッシュを計算して前回のハッシュ値と照合。一致していれば内容同一として Embedding 計算をスキップ。
  - 新規または SHA-256 が変更されたファイルのみ Embedding 計算を実行。
- **除外キーワード・拡張子の完全連動**:
  - Web画面の差分同期（⚡）や全件再作成（🔄）、全文検索連動時など、あらゆるインデックス処理において設定された除外キーワード（`exclude_keywords.txt`）および拡張子設定（`index_selected_extensions.txt`）を厳格に適用。
  - 絶対パス指定（`/path/to/...`）、相対パス/ディレクトリ名指定、単語境界（トークン完全一致による誤爆防止）、隠し要素（`foo/.`）を全文検索側と同等に正しく除外判定する。
  - 語の区切りを持たないキーワードは部分一致で判定する: 非 ASCII を含むもの（`旧` など）と、記号だけで 2 文字以上のもの
    （`~$` は Office の一時ファイル `~$draft.docx` に一致する）。ドットだけのキーワードは、ほぼすべての名前に一致するため部分一致にしない。
  - 判定の実装は全文インデックスと共通（`backend/app/services/exclude_rules.py`）。
  - 除外キーワードが変更・追加された際は、既存の全文検索DBおよび全モデル分のベクトルDBから除外対象ファイルを即座に自動パージ（クリーンアップ）する。
  - 拡張子を除外した場合の既存インデックスの削除は、削除確認で許可されたとき（`clean_excluded_files=True`）だけ行い、同じく全モデル分のベクトルDBが対象になる。
- **推論のまとめ方**:
  - 1 ファイルにつき、文書ベクトル（本文先頭 1000 文字）と全チャンクのベクトルを 1 回のバッチ推論で生成する。
- **失敗したファイル**:
  - 抽出や推論に失敗したファイルは警告ログに記録して次のファイルへ進む。DB には登録されないため、次回の差分同期で再試行される。
- **削除の保護**:
  - 走査で見つからなくなった文書の削除は、明示的に許可された場合（`clean_deleted_files=True`）だけ行う。全文インデックス連動の自動同期では削除しない。
  - 到達不能な対象フォルダ（未接続のネットワークドライブ、取り外した外部ドライブなど）配下の文書は、削除を許可していても削除候補にしない。
  - 削除候補は対象フォルダの指定に関係なくベクトルDB全体から求める。対象フォルダを一部だけ指定して削除を許可すると、指定外のフォルダの文書も削除候補になる点に注意（画面からの差分更新は常に全有効フォルダを指定する）。
- **走査範囲は全文インデックスと同じ**:
  - 走査は全文インデックスと同じ関数（`services/file_walker.walk_indexable_files`）で行う。除外キーワード・拡張子に加えて、
    検索対象ごとの階層数（`index_depth`）も同じ数え方で適用する。
  - ドット始まりのフォルダや `node_modules` / `dist` / `build` を特別扱いしない。対象から外したいものは除外キーワードに書く
    （既定の除外キーワードには `.git` / `node_modules` / `__pycache__` などが入っている）。
  - `POST /api/vector/index/start` で対象フォルダを指定しないときは、有効なローカル検索対象を、登録された階層数で走査する。
    フォルダを明示したときは、その配下をすべて走査する。
- **全件再作成（`force_reindex`）**:
  - 既存の文書を残したまま、変更の有無に関係なく全ファイルを作り直す（文書は 1 件ずつ置き換わる）。
  - 最後まで終わったときだけ、走査で見つからなかった文書を消す。途中で止まった場合は何も消さないので、検索できる状態が残る。
  - 到達不能な対象フォルダ配下の文書は、全件再作成でも消さない。
- **中止**:
  - `POST /api/vector/index/cancel` で実行中のインデックス作成を中止できる。処理中のファイルが終わった時点で止まり、
    そこまでに保存した文書は残る。結果の `cancelled` が `true` になる。
- **自動連動**:
  - ファイルの変更通知を受けたバックグラウンドの差分更新（`ChangeTrackingService`。`IndexService` をベクトル同期ありで使う）では、
    全文インデックスの更新が終わると、同じフォルダ・除外キーワード・階層数でベクトルインデックスの差分同期
    （`vector_state.sync_index`）を行う。
  - 画面からの再インデックスと検索前の更新（リクエストの中で行う全文インデックスの更新）では、応答を待たせないよう
    ベクトル同期を行わない。ベクトル側は、次の変更通知か、ベクトル管理画面の差分更新で反映する。
  - 同期は「インデックス実行中」（`index_runs.is_running`）を解除したあとに行う。Embedding の生成が長くても、
    その間の他フォルダの再インデックス要求は 409 にならない。
  - ベクトル同期は同時に 1 つだけ実行する。実行中に来た差分同期の要求は捨てずに覚えておき、今の同期が終わったら続けて実行する。
- **アーキテクチャ・フロー図**:
  - `docs/vector_diff_and_exclude_flow.excalidraw.md` 参照。


## 7. 類似語・専門用語の一元連携（Glossary）
- 専門用語辞書は個別の Excel ファイル管理を廃止し、検索ルール管理の `synonym_groups.txt`（形式: `用語1,用語2,... : 意味・解説`）を単一データソースとして一元統合。
- 意味検索（ハイブリッド / ベクトル / AIインプット）時は、`GlossaryDictionary` が `synonym_groups.txt` を自動ロードし、最長一致アルゴリズムでクエリから用語を検出して表記揺れ・意味展開に活用。
- 通常キーワード検索時はコロンより前の類似語のみを OR 展開に利用し、解説文は混入させない。
- 検索ルール管理画面での保存時（`PUT /api/index/settings`）に `vector_state.reload_glossary()` が連動実行され、ベクトル辞書も即座にホットリロード。

## 8. 一致理由バッジ & 核心文 (Salient Sentence) & スコア正規化
- **一致理由バッジ (`match_source` / `match_type`)**:
  - API は各結果に `match_type`（`both` / `vector_only` / `keyword_only`）と、そこから導出した `match_source`（`both` / `vector` / `keyword`）の両方を返す。
  - Web UI・macOS / Flet ランチャー・Windows WPF ランチャーは `match_source` を読んでバッジを表示する。
    - `both`: キーワード検索とベクトル検索の両方でヒット（`🌟 両方一致`）
    - `vector`: ベクトル検索による意味的類似でヒット（`🔮 意味一致`）
    - `keyword`: キーワード検索でヒット（`🏷️ キーワード一致`）
  - `match_source` はモデル（`SearchResultItem`）の算出項目で、`match_type` と食い違うことはない。
- **核心文 (`salient_sentence`)**:
  - ヒットしたチャンクを句点・改行で文に分け、クエリの単語（空白・カンマ区切り、2 文字以上）を最も多く含む一文を抽出し、検索結果カードにハイライト表示する。
- **RRFスコアの正規化（0.0〜1.0 / 0%〜100%）**:
  - RRFスコアは理論上の最大値（両方1位の場合: $S_{\max} = \frac{w_v + w_k}{k + 1}$）で除算して $0.0 \sim 1.0$ に正規化。
  - これにより、両方1位で `100.0%`、片方1位で `約50.0%`、片方2位で `約49.2%` となり、UI上で直感的なパーセント表示（`融合スコア: XX.X%`）を提供する。
- **並び替え機能（スコア順ソート & default時のハイブリッド順位優先）**:
  - 並び替えオプションに「ハイブリッドスコア順 (`hybrid_score`)」「ベクトル類似度順 (`vector_score`)」「通常検索スコア順 (`keyword_score`)」を提供。
  - デフォルト（`default`）ソート選択時は、ハイブリッド検索結果（`hybrid_score` 保持アイテム）に対して **ハイブリッド融合スコア降順（RRF順位）** を第1優先とし、同点時のみ従来のファイル名一致レベルや更新日でタイブレークする。

## 10. ベクトル管理画面 (PoC 同等以上の管理 UI)
- **モデル別ステータスバッジ**:
  - 超軽量（30M）、標準（70M）、高精度（310M）各モデルのインデックス済みドキュメント件数、DBファイルサイズ（MB）、未インデックス状態をカードヘッダーにバッジ表示。
- **差分インデックス更新 ⚡ vs 全件再インデックス 🔄**:
  - 更新ボタンを2つに明確分離。差分更新は mtime / sha256 比較で未変更ファイルをスキップし数秒で完了。
  - プログレスバー（アニメーション付き）と完了サマリー（新規、更新、スキップ、削除、所要時間、DBサイズ）を可視化。
  - 実行中は「中止」ボタンを表示する。中止した場合、完了サマリーは「中止しました」と表示し、そこまでの件数を示す。
  - 全件再インデックスの開始前に、既存のインデックスは置き換わるまで残ること、最後まで終わると存在しなくなったファイルの
    インデックスが削除されることを確認する。
- **類似語・専門用語の一元連携**:
  - ベクトル管理画面内の個別辞書エディタは廃止し、「検索ルール管理」の「類似語・専門用語リスト」へ一元化。ヘッダーに検索ルール管理への連携案内バッジを表示。
- **単一ファイル差分更新ベンチマーク**:
  - サーバー上のファイルパスを指定して 1 ファイルを差分更新し、ハッシュ I/O・チャンク化・推論・DB 書き込みの所要時間（ミリ秒）とチャンク数を表示する（`POST /api/vector/index/update-file`）。
  - 意地悪テスト用プリセット4種（長文、空、記号・HTMLタグ、見出し多用）は、画面で作った本文を送ってチャンク化と推論の時間だけを測る
    （`POST /api/vector/benchmark/text`）。ファイルもインデックスも変更しない。
## 11. 除外キーワード（Exclude Keywords）のファイル名適用
- **ファイル名に対する除外フィルタ**:
  - 除外キーワードは文書本文（中身）ではなく、ファイル名（またはパス）に対する除外フィルタとして機能する。
  - 通常検索（FTS5）、ベクトル検索（`v_res.results`）、ハイブリッド検索（`final_items`）のすべてにおいて、ファイル名（またはステム）に除外キーワードが含まれるファイル（例: `gantt_diff_summary.json` や `2026_gantt_diff_summary_v1.md` 等）を完全に除外。
- **誤除外防止（記号/単語境界ガード）**:
  - `old`, `env`, `bin`, `git` などの4文字以下の短い英数字キーワードについては、`older.md`, `environment.md` 等の通常ファイルへの過剰除外を防ぐため、記号/単語境界でのみ一致判定する。

## 12. モデル切替とインデックス開始の堅牢性
- **モデル未指定・変更時の自動ロード連動**:
  - UI上でモデルカードを選択後、明示的な「モデルをロード」ボタンを押下せずに「⚡ 差分更新」や「🔄 全件再作成」を開始した場合でも、選択されたモデルが未ロードあるいは現在と異なるモデルであれば、自動的に対象モデルのロードを実行してからインデックス処理を開始する。
  - API エンドポイント `POST /api/vector/index/start` は `model_path` を受け付け、指定モデルが未ロードであれば自動でロードした上でインデックス同期を実行する。
- **対象フォルダ未指定時のフォールバック**:
  - `target_folders` がリクエストに含まれない場合、DB（SQLite）の `targets` テーブルから現在有効なローカル検索対象フォルダ群を自動で抽出し、安全に全件を対象としてインデックス作成を開始する。

## 13. アクティブ（稼働中）モデルの視覚的強調ハイライト
- **稼働状態の最優先可視化**:
  - 現在バックエンドでロードされ検索・インデックス処理に利用可能なモデルカードに対し、発光枠線（`boxShadow`）、背景色強調、および「🟢 稼働中 (アクティブ)」バッジを付与。
  - 画面表示時やモデルロード時に、稼働中のモデルタイプ（`ruri-v3-310m` なら標準モデル、`ruri-v3-30m` なら超軽量モデル）へ選択状態を自動同期し、非稼働モデルの誤ハイライトを完全に排除。
- **選択状態（切替準備）との明確な区別**:
  - ユーザーが未ロードのカードをクリックした際は「👉 選択中 (未ロード)」バッジおよび点線枠線を表示し、ロードボタンを「🚀 選択したモデルをロードして切替」に更新して直感的なモデル切替操作を支援する。

## 14. インデックス作成中のリアルタイム状態可視化
- **初回ロードからの自動検知**:
  - `refreshData()` 内で `fetchVectorIndexProgress()` を初期取得し、画面を開いた時点で既にバックグラウンドでインデックス処理が実行中であっても即座に検知して 800ms 間隔の定期ポーリングを開始する。
- **画面全体のマルチインジケーター**:
  - **ページヘッダー**: タイトル横に「🔄 ベクトルインデックス作成中... (XX%)」の発光バッジを表示。
  - **インデックス管理パネル**: 発光アクセント枠線（`boxShadow`）および「🔄 インデックス同期中」バッジを表示。
  - **稼働中モデルカード**: 稼働中バッジ内に「🔄」スピナーを表示。
  - **操作ボタン**: 実行中のボタンがローディング表示となり、ボタンの二重押下を排他ガード。

## 15. モデル選択の永続化 (`config.json`) とサーバー起動時自動復元
- **モデル選択の自動保存 (`config.json`)**:
  - ユーザーがモデル（超軽量 `ruri-v3-30m` / 標準 `ruri-v3-310m` 等）を選択またはロードすると、`VectorState.save_model_selection()` により `backend/data/config.json`（またはルート `config.json`）へ選択モデルのパス・モデル名・更新日時が即座に記録される。
  - テスト用のダミーモデル（`mock_model`）等は保存されず、設定ファイルの汚染を防止する。
- **サーバー起動時（Lifespan）の自動ロード**:
  - FastAPI の起動時コンテキスト（`lifespan`）にて `config.json` に有効な記録が残っている場合のみ `vector_state.load_saved_model()` が呼び出され、前回のモデルを自動的にロードする。
  - 初回起動時やモデル未選択時（記録なし）はモデルを自動ロードせず、未ロード状態で安全に待機する（勝手なデフォルトモデルのロードを行わない）。
- **即時検索の保証（ノンストレス運用）**:
  - サーバー再起動直後であっても、記録が残っていればユーザーが設定画面を開いてモデルをロードする必要はなく、最初から前回使用していたモデルでハイブリッド検索・ベクトル検索・AIインプットが即座に機能する。
- **UI連携**:
  - ベクトル管理画面のモデル選択カード下部に、現在記憶されているモデル情報（`config.json` の内容）をインライン表示し、ユーザーが永続化状態を把握できるようにする。

## 16. デバイス自動検出 & GPU加速 (MPS / CUDA) と CPU フォールバック
- **デバイス優先判定**:
  1. 環境変数 `VECTOR_DEVICE`（明示指定がある場合は最優先）
  2. NVIDIA CUDA (`torch.cuda.is_available()`): Windows RTX A500 等で自動適用
  3. Apple Silicon Metal (`torch.backends.mps.is_available()`): Mac 環境で自動適用（実測で CPU 比約 7.2 倍高速化）
  4. CPU: 非対応環境、初期化エラー、OOM 発生時等の自動フォールバック先
- **自己修復・フォールバック機能**:
  - モデルロード時（`Embedder.__init__`）やエンコード推論時（`encode`, `encode_batch`）に、万一 GPU ドライバ異常やメモリ不足（OOM）が発生した場合、プロセスを終了させずに自動的に `self.device = "cpu"` にフォールバックして処理を継続する。
- **バッチ処理最適化**:
  - GPU の高い並列演算性能を引き出すため、最適なバッチサイズで一括エンコードを実施。
- **CPU 推論のスレッド数**:
  - 既定は 1 スレッド（Apple Silicon 上でのスレッド競合クラッシュを防ぐため）。
  - 環境変数 `SEARCH_APP_NATIVE_THREADS` に 2 以上の整数を指定すると、そのスレッド数で CPU 推論を行う。CPU のみの Windows 環境で Embedding 生成が遅い場合の切替用。
  - torch と faiss の OpenMP 二重初期化による異常終了を防ぐ設定（`KMP_DUPLICATE_LIB_OK`）を含め、これらの環境変数は `backend/app/runtime_env.py` が `app` パッケージの import 時に設定する。利用者が設定済みの値は上書きしない。
- **ステータス API と UI 可視化**:
  - `GET /api/vector/model/status` に `device`, `device_name`, `cuda_available`, `mps_available` を追加。
  - ベクトル管理画面のヘッダー最上部に常時表示のデバイスバッジ（`⚡ GPU稼働中: Apple Silicon (Metal)` / `⚡ GPU稼働中: NVIDIA RTX A500 (CUDA)` / `💻 CPU稼働中 (フォールバック)`）とデバイス名を表示。
- **Windows NVIDIA GPU (RTX A500) 向けセットアップ環境**:
  - `backend/requirements-cuda.txt`: PyTorch 公式の CUDA 12.4 対応 wheel を自動解決してインストール。
  - `setup_windows_cuda.bat`: 仮想環境作成から CUDA 版 PyTorch インストール、GPU 動作検証までをワンクリックで実行可能。
  - `start_windows.bat`: 起動時に現在の実行環境（CUDA or CPU）をコンソール上に表示。

## 17. FAISS 高速エンジンと NumPy 自動フォールバック（未導入時のUI可視化）
- **高速ベクトル検索エンジン (`FAISS`)**:
  - `faiss-cpu`（または `faiss-gpu`）がインストールされている場合、`FaissVectorIndex` は `faiss.IndexFlatIP`（正規化済みベクトルの内積計算）を用いて数万〜数十万件のチャンクを数ミリ秒で検索する。
- **NumPy 自動フォールバック (`FaissVectorIndex`)**:
  - 一部の Windows 環境や Python バージョンで prebuilt wheel が提供されていない場合や、オフライン環境等で FAISS がインストールされていない場合でも、プロセス起動を阻害しない。
  - `import faiss` 失敗を安全に捕捉し、`HAS_FAISS = False` を検出。
  - FAISS 未導入時は、NumPy の行列内積計算（`np.dot`）および `np.argpartition` による上位 K 件探索へ自動でフォールバック。計算結果は FAISS と完全に等価であり、動作が保証される。
- **API および UI での稼働状態可視化**:
  - `GET /api/vector/model/status` に `has_faiss: bool` を追加。
  - **ベクトル管理画面の最上部ヘッダー**: 稼働デバイスバッジの横にベクトルエンジンバッジ（`⚡ エンジン: FAISS (高速)` または `⚠️ エンジン: NumPy (フォールバック / faiss未導入)`）を常時表示。
  - **モデル選択カード**: 右上バッジ群にエンジン状態を表示。
  - **インストール案内バナー**: `has_faiss === false` の場合、モデル設定パネル内に `pip install -r backend/requirements.txt` または `pip install faiss-cpu` の手順を記した警告ガイダンスバナーを表示し、導入方法を一目で把握できるようにする。

## 18. インデックス対象拡張子の連動適用（検索ルール管理との統合）
- **対象拡張子の設定連動**:
  - 「検索ルール管理」画面の「インデックス対象拡張子」カードで保存された選択拡張子（`index_selected_extensions`）および追加拡張子（`custom_content_extensions`, `custom_filename_extensions`）を、ベクトルインデックス作成（`VectorIndexManager`）へ自動適用。
  - ユーザーがチェックを外した拡張子のファイルはベクトルDBの走査対象から完全に除外され、不要な埋め込み計算やストレージ消費を防止する。
  - 追加した本文用拡張子（`.py` 等）は汎用テキスト抽出エンジン経由で本文チャンクが生成され、追加したファイル名のみ拡張子はファイル名テキストとしてベクトル化される。
- **検索時の拡張子フィルタ適用**:
  - 検索リクエスト（`extensions` または `index_types`）で拡張子が指定されている場合、キーワード検索だけでなくベクトル検索結果（`v_res.results`）に対しても同一の拡張子フィルタリングを適用し、指定外拡張子の結果を除外する。
