# Vault のルール

この Vault は、第二の脳として育てていく Obsidian のノート集です。ノートは Markdown で書かれています。

## スキルとエージェントを先に使う

自分の知識や手作業で済ませる前に、合うスキル(`skill` で読み込む)かエージェント(子に任せる)を使う。**迷ったら使う。** 頼まれなくても使う。スキルがプロジェクトの中に無ければ、`~/.config/opencode/skills/` を見る。

- **人・案件・手続き・連絡先・過去の記録・社内の決まりを聞かれたら、答える前に `finder` でローカルの資料を探す。** 一般論で答えない。見つからなければ、探した語と場所を書いて「見つからなかった」と答える。人については、先にスキル `people` で人物ノートを引く(who)。
- **調査は、1 回で答えまで出す。** 見つけたファイルは、「読んでよいか」と聞かずに読む。子が場所だけを返したら、止まらずに続けて読む(作業フォルダの外のテキストは、スキル `file-finder` の read コマンド。Word・Excel・PDF は `doc-convert`。多ければ `researcher`)。途中で聞くのは、結果が大きく変わる曖昧さがあるときだけ。

| 依頼 | 使うもの |
|---|---|
| ファイルを探す、「〜はどこ」、資料の 1 か所で答えが出る問い | `finder`(探して、読んで、答えまで返す) |
| 「〜について調べて」、Word・Excel・PowerPoint・PDF・長い文書を読む | `researcher`(探すところから任せる。先に `finder` を呼ばない) |
| 計算・単位の換算・判定(暗算しない) | `calc-check` |
| 手順書・マニュアル・長い資料を書く / 依頼が曖昧 | `doc-writing` / `interview` |
| 書いた文を整える | `yomiyasu`(長い文書は `polish`) |
| ノートに保存する・直す / 議事録 | `vault-notes` / `meeting-notes` |
| 図を作る / 図を読む | `diagram` / `diagram-reader` |
| タスク・期限、Git の差分、自作のアプリ | `app-ecosystem` |
| メール・予定 | `outlook`(受信と送信のキャッシュから探すので、期間や条件を聞き返さずに任せる) |
| 登場人物(自分も)を引く・覚える | `people`(覚えるのは `/people` のインタビューで) |
| Web を読む / Web の操作の自動化 | `browser` / `browser-session` |

## Vault の構成

| フォルダ | 役割 | 触り方 |
|---|---|---|
| `01_data/` | ノート本体。`01_data/年/月/日/` の形で、作った日ごとのフォルダに置く | 依頼されたノートだけ変更してよい |
| `01_data/000_適宜移す/` | 仮置き場(`00_inbox`、`90_資料`、`99_日次記録` など)。あとで人間が整理する | 勝手に整理・移動しない |
| `01_data/common_image/` | 共通で使う画像 | 触らない |
| `02_MOC/` | 目次ノート(MOC) | 依頼されたときだけ変更する |
| `05_people/` | 人物ノート(1 人 1 ノート。自分も)。業務の事実だけを書き、電話番号・私生活・人物の評価は書かない | スキル `people` で作る・足す(ユーザーの承認の後)。直接は書き換えない |
| `03_Dataview/` | Dataview で作った点検用のノート(空のファイル、同名ファイル、無題のファイルなど) | 依頼されたときだけ変更する |
| `04_pptx/` | Markdown から PowerPoint を作るためのビルド用ファイルと出力 | 触らない |
| `10_summary/` | AI が作った要約。名前は `元のノート名_summary.md` | 新しい要約は、ここに別のノートとして作る |
| `11_common_prompt/` | AI に渡す共通の指示 | 触らない |
| `00_templates/` | Templater のテンプレート | 触らない |
| `70_gantt_csv/` | ガントチャートから出力された CSV と差分 | 触らない(自動生成) |
| `80_script/` | Templater などのスクリプト | 触らない |
| `90_batch/` | 補助のバッチファイル | 触らない |
| `Excalidraw/`、`Analysis/`、`Parts/`、`Media/` | 図と 3D CAD 関係の成果物 | 触らない |
| `scratch/`、`temp/` | 一時的な作業用 | 中身は残る前提にしない |
| `.obsidian/`、`.smart-env/`、`.excalidraw-cache/`、`.claudian/`、`.trash/` | Obsidian とプラグインの設定、キャッシュ、ゴミ箱 | 触らない |
| `.handoff/` | サブエージェントが詳細の結果を書く使い捨てのフォルダ。ドットで始まるので Obsidian には表示されない。Vault の `.gitignore` に入れておく | サブエージェントの結果を読むときだけ読む。ノートとしては扱わない |

## ノートの書き方

- 新しいノートの先頭には、次の frontmatter を付ける。

  ```
  ---
  created: 2026-01-01 09:00:00
  tags:
  ---
  ```

  `created` には、作った日時を `YYYY-MM-DD HH:mm:ss` の形で書く。
- **AI が作ったノートの印:** ハーネス(OpenCode)が作ったノートには、frontmatter に `ai_generated: opencode` と `ai_reviewed: false` が付く。Obsidian では `ai_reviewed` がチェックボックスになる。**人が内容を確かめたら ✓(`true`)にする。✓ になるまで、AI はそのノートを根拠にしない**(原典を探す手がかりにだけ使う)。印の無いノートは、人が書いたノートとして扱う。`10_summary/` の要約は、印が無くても AI のまとめとして扱う。
- **AI が直したノートの印:** ハーネスが既存のノートを直すと、frontmatter に `ai_edited`(直した日時)が入り、`ai_reviewed` が `false` になる(frontmatter の無いノートには、この 2 つだけが付く)。**AI は、直したノートを根拠に使ってよい**。印は、人がレビュー漏れを確かめるためのもの。確かめたら ✓ にする。AI が作ったノート(`ai_generated`)を ✓ の後に AI が直すと、`false` に戻り、✓ にするまで根拠にされない。
- 未レビューの一覧: ハーネスに「レビューが残っているノートは?」と聞く(`vault-notes` の `unreviewed`。印の付け忘れの疑いも出る)。Dataview なら ` ```dataview` / `TABLE created, ai_edited FROM "01_data" WHERE (ai_generated OR ai_edited) AND !ai_reviewed SORT file.mtime DESC` / ` ``` `
- 文章は「である調」で書く。検討や検証のノートは、結論・結果を最上部に書く。
- タグはシンプルにする。階層(`a/b` のようなネスト)は使わない。新しいタグを作る前に、既存のタグを検索して、同じ意味のものがあればそれを使う(`vault-notes` の `tags --grep 語` で、使われているタグと件数を調べられる。綴りも既存のままにする)。
- ノート間のリンクは `[[ノート名]]` の形にする。**AI が新しいノートを作るときは、関連する既存のノートを探して(`vault-notes` の `related 語…`)、リンクを入れる**。本文のその語の箇所に `[[ノート名]]` を書き、足りなければ末尾の `## 関連` に `- [[ノート名]] — 関連の理由` で並べる。探した結果に無いノートは、リンクにしない。
- 画像や図の埋め込みは、`![[ファイル名]]` の形に保つ。画像のパスや `<img>` タグに書き換えない。
- 元のノートの frontmatter と見出しの構成は、依頼がない限り変えない。
- ファイル名に `\ / : * ? " < > |` は使わない。
- 新しいノートは、指定されたフォルダに作る。指定がなければ、置き場所を質問する。ふだんの置き場所は、その日の `01_data/年/月/日/`。

## ノートの保存・修正とプラグインの実行

- 検討した結果の保存と、既存のノートの修正は、スキル `vault-notes` の手順で行う。頼まれたときだけ行う。
  - 日付と時刻は、推測せず、そのスキルの `today` で取る。新しいノートは、今日のフォルダー(`01_data/年/月/日/`)に作る。
  - 既存のノートの修正は、修正の前にバックアップを取り、変更前と変更後を示して、承認を得てから、最小の変更だけを入れる。
- Obsidian のプラグインやコマンドの実行は、サブエージェント `obsidian` に任せる。実行できるのは、人間が許可リストに書いたものだけ。
- 複数のノートを探して読む作業は、`researcher` に任せる。

## 図(Excalidraw・draw.io)

- **図は、画像として見られない。** 図(`.excalidraw.md`、`.drawio`、`.drawio.svg`、`.dio.svg`)を読むときは、スキル `diagram-reader` の `describe` で、箱・矢印・レーンを文章にして読む。ノートに `![[名前.excalidraw]]` や `![[名前.drawio.svg]]` の埋め込みがあれば、`links` で場所を探してから読む。図の中身が分からないまま、ノートの内容を説明しない。
- Excalidraw の図を作るのは、サブエージェント `diagram`(コマンド `/diagram`)。フロー図・スイムレーン・ツリー・マインドマップに対応している。名前は `図_話題.excalidraw.md`、保存先は、ユーザーの指定が無ければ、対象のノートと同じフォルダ。draw.io の図は、読むだけ(作らない)。
- 既存の図は、上書きしない。直すときは、`describe` で読んで、新しい図として作り直す(古い図は、人が消す)。
- 圧縮されたデータ(`compressed-json`)を手で書き換えない(下の「触らないもの」)。

## 触らないもの

- 上の表で「触らない」とされたフォルダの中。
- `.excalidraw.md` のファイル。中身は圧縮されたデータで、文章として編集すると壊れる。読んで内容を説明するだけにする。
- 画像、PDF、CAD などの添付ファイル(`.md` 以外)。移動・削除・名前の変更をしない。
- Templater や Dataview のコードブロック(`<% %>`、`<%* %>`、` ```dataview `)。依頼がない限り書き換えない。

## 名前の変更・移動・削除

- ノートの名前を変えたり移動したりすると、ほかのノートからのリンクが切れることがある。実行する前に、そのノートを指している `[[ノート名]]` を検索して、影響を受けるノートの一覧を示し、確認を取る。
- ノートを削除するときは、そのノートに関連する添付ファイル(画像や PDF)も一緒に消すかどうかを、別に確認する。
- 完全に消さず、`.trash/` などの退避先へ移す方法を先に提案する。

## 作業のしかた

- 「探して」と頼まれたら、見つかったノートのパスと、該当する部分を示す。見つからなかったときは、見つからなかったと答える。推測で補わない。
- 要約や整理は、ノートに書かれていないことを足さない。出典(どのノートの内容か)を示す。
- 要約や整理の結果は、元のノートを上書きせず、別のノートとして作る。上書きしてよいのは、依頼されたときだけ。
- 複数のノートを一度に変更するときは、変更する前に、対象の一覧を示して確認する。

## Vault のカスタマイズを直すとき

(スクリプトやプラグインのソース、`docs/` がある Vault だけ)

- 仕様書は `docs/` にある。仕様書と実装が食い違っていたら、実装を正として、仕様書を直す。
- Templater のスクリプトの本体は `80_script/register_custom_commands/` にある。ファイルを追加・改名したら、`00_templates/RegisterCustomCommands.md` の一覧も直す。
- プラグインのソース(`.ts`)の変更とビルド(`npm test`、`npm run build`)は、自宅で行う。会社の PC では `npm install` ができず、ビルドできない。会社では、ビルド済みの `main.js`(Git で管理している)を直接編集しない。
- スクリプトを書くときは、Python(`pip install` が使える)か、標準モジュールだけの Node.js を使う。
- `*.excalidraw.md` に仕様のコメントを書くときは、frontmatter の直後に書く。前に書くと、Obsidian が図として開けなくなる。
