# 【プロジェクト名】

【このプロジェクトが何をするものか、1〜2 行で書く】

## コーディングの決まり(C#)

- C# 専用のスキルは無い。この節に従う。コードを書く・直す・レビューする前に、`README.md`、`.sln`・`.csproj`、`Directory.Build.props`、`.editorconfig`、変える所の周りのコードとテストを読む。**既存の書き方(名前、構成、テストの形)と `.editorconfig` が、この節より優先する。**
- コードの調査は、リポジトリの中を直接読む(read・grep・glob)。社内の資料の検索(`finder`・`researcher`)は、仕様書や原典の資料を探すときだけ使う。
- 標準ライブラリ(BCL)で足りるなら、それを使う。パッケージ(NuGet)を足すのは、標準で無理なときだけ。足す前にユーザーに確認し、バージョンを固定する。
- 型と名前: `Nullable` を有効にし、`#nullable disable` や `!`(null 許容の抑止)で警告を逃れない。型・メソッド・プロパティは `PascalCase`、引数・ローカル変数は `camelCase`、private フィールドは既存に合わせる(`_camelCase` が多い)。インターフェースは `I` で始める。**単位は名前かコメントに書く**(`LengthMm`、`forceN`)。
- 関数は小さく、1 つの仕事にする。計算(入力から値を返すだけ)と、入出力(ファイル、画面、ネットワーク、データベース)を分ける。計算はテストしやすくする。`static` な可変の状態を増やさない。
- コメントは日本語。公開するクラス・メソッドには、XML ドキュメントコメント(`///`)で、何を受け取り何を返すか、単位、出す例外を書く。コメントは「なぜ」を書く。
- 例外: 具体的な型を出し、具体的な型で受ける。`catch (Exception)` で握りつぶさない。引数は早めに検査する(`ArgumentNullException.ThrowIfNull` など)。再 `throw` は `throw;`(`throw ex;` にしない)。
- 非同期: `async` / `await` を使い、`async void` はイベントハンドラ以外で使わない。`.Result`・`.Wait()` でブロックしない。長い処理には `CancellationToken` を渡す。
- `IDisposable` は `using` で解放する。外部プログラムを起動するときは、`UseShellExecute = false` で、引数を配列(`ArgumentList`)で渡す。
- 文字コード: ソースは UTF-8(BOM の有無は既存に合わせる)。ファイルの読み書きは `Encoding` を明示する。日本語の Windows で作られた古いファイル(cp932)を扱うときは、.NET Core 以降では `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)` を先に呼ばないと、`Encoding.GetEncoding(932)` が使えない。
- パスは `Path.Combine` で組み立てる(区切り文字を文字列で書かない)。決め打ちせず、設定か引数で受け取る。
- 浮動小数点の等しさは、許容差で比べる。お金や桁を厳密に扱う値は `decimal`。換算の係数は、名前を付けた定数にして、出典をコメントに書く。
- 接続文字列、パスワード、API キーをコードやテストに書かない。設定ファイルに入れるときは、Git に入れない(`appsettings.Local.json` など。ユーザーに確認する)。
- 警告をなくすために、`#pragma warning disable` や `[SuppressMessage]` を足さない(どうしても要るときは、理由をコメントに書く)。

## 作業の進め方

- 作業を始める前に、`README.md` と `docs/` の関係する文書を読む。
- 変更の前に、`git status` で状態を確認する。未コミットの変更は、勝手に戻さない・消さない。
- コミットは、頼まれたときだけ行う。`git push` と、履歴の書き換え(`reset --hard`、`rebase` など)はしない。
- 新しい機能や不具合の修正は、テストを先に書く(テスト駆動)。先に失敗することを確認してから、実装する。テストの枠組みは【既存のテストプロジェクトに合わせる(xUnit・NUnit・MSTest など)】。テストを通すために、テストを消す・弱める・スキップすることはしない。
- コード、ドキュメント、画面の文言は日本語で書く。
- 動作や計算の中身を変えたら、関係する `docs/` の文書も、同じ変更の中で直す。コードと文書が食い違っていたら、どちらかに勝手に合わせず、報告して確認する。
- 既存の書き方と構成に合わせる。新しいパッケージは、先に確認してから追加する。依頼の外のリファクタリング・整形・名前の変更はしない。

## 計算・解析(設計計算、構造計算、CAE など)

- 単位系を決めて、この節か `docs/` に書く(【例: N、mm、MPa】)。違う単位を混ぜない。変数名かコメントに、単位を書く。
- 数値(材料定数、許容値、荷重、規格の値)を、作り上げない。出典(規格・文献・社内基準の名前、版、条項、ページ)を、入力データか文書に残す。出典が分からないものは「未確認」と書く。
- 入力(条件・パラメータ)、モデル、結果を分けて保存する。結果は、入力とプログラムから作り直せる形にする。手で書き換えた結果を、そのまま置かない。
- 結果は、手計算、既知の解、過去の結果のどれかと照合して、差を記録する。テストの期待値も、手計算・既知の解・規格の例から取り、実装を動かした結果をそのまま期待値にしない。照合していない結果は「未検証」と書く。
- 解析ソフト(ソルバー)は、この PC で実行できないことがある。実行して確かめられなかった解析や結果は、「未実行」と書く。
- 設計の結論(合否、安全率、採用する寸法)は、案として示す。最終の判断は人間が行う。

## Git で管理するもの・しないもの

- 管理する: ソースコード、`.sln`・`.csproj`、`Directory.Build.props`、`global.json`、`.editorconfig`、`NuGet.config`、`packages.lock.json`(使っているとき)、入力データ(条件・パラメータ)、`docs/`、小さな基準の結果。
- 管理しない: `bin/`、`obj/`、`.vs/`、`*.user`、`TestResults/`、`.handoff/`、ソルバーが出す大きな結果ファイルや一時ファイル(【拡張子を書く】)。`.gitignore` に無ければ足す(`dotnet new gitignore` で雛形を作れる)。
- バイナリのモデルファイル(【例: CAE のモデル】)は、差分が見えない。大きいものを Git に入れる前に、確認する。変更したら、何を変えたかを `docs/` か変更履歴に書く。

## 会社の PC で使える言語とパッケージ

- .NET SDK(`dotnet`)が会社の PC に入っているか、使える版は【確認した結果を書く。未確認なら「未確認」】。
- NuGet からのパッケージの取得(`dotnet restore`、`dotnet add package`)が会社の PC でできるかは【確認した結果を書く。未確認なら「未確認」】。できないとき・未確認のときは、取得を何度も試さない。失敗したら、そのまま報告する。必要なパッケージは、人間が運ぶ(ユーザーに確認する)。
- ビルドやテストを会社の PC で実行できなかったときは、報告に「実行できなかった」と書く。
- 補助のスクリプトに Python を使うときは、スキル `python-env` の手順に従う(`pip install` は、`requirements` にあるか、ユーザーが名前を指定したパッケージだけ)。Node.js は `npm install` や `npx` でパッケージを取得できない。

## Windows の会社 PC で動かすもの

- `.bat` ファイルには、日本語を書かない(ASCII だけにする)。会社の PC では、行が誤って解釈されることがある。
- パスは、大文字と小文字を区別しない前提で書く。名前の大文字小文字だけが違うファイルを、同じフォルダに作らない。
- Windows でしか動かない部分(WPF、WinForms、.NET Framework、COM、レジストリ、Excel・Outlook などの自動操作)は、Mac では実行して確認できない。変更したら、確認できていないことを報告に明記する。

## サブエージェントの受け渡し用フォルダ

- サブエージェントが詳細を書く `.handoff/` は、このプロジェクトのルート直下にできる。使い捨てなので、Git には入れない。`.gitignore` に `.handoff/` が入っていることを確認する(なければ足す)。

## 確認が必要な操作

- ファイルの削除や名前の変更(コードから呼び出されている可能性があるため)
- 入力データ、モデル、基準の結果の上書き。許容値や規格の値の変更
- NuGet パッケージの追加・更新・削除。対象のフレームワーク(`TargetFramework`)や `global.json` の SDK の版の変更

- 外部のシステムへ送信する処理や、自動で実行される処理の追加
- 発行(`dotnet publish`)した成果物の、会社の環境への配置
