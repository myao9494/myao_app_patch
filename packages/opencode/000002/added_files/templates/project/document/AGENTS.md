# 【プロジェクト名】

【この資料が何のためのものか、1〜2 行で書く】

## スキルとエージェントを先に使う

自分の知識や手作業で済ませる前に、合うスキル(`skill` で読み込む)かエージェント(子に任せる)を使う。**迷ったら使う。** 頼まれなくても使う。スキルがプロジェクトの中に無ければ、`~/.config/opencode/skills/` を見る。

- **人・案件・手続き・連絡先・過去の記録・社内の決まりを聞かれたら、答える前に `finder` でローカルの資料を探す。** 一般論で答えない。見つからなければ、探した語と場所を書いて「見つからなかった」と答える。
- **調査は、1 回で答えまで出す。** 見つけたファイルは、「読んでよいか」と聞かずに読む。子が場所だけを返したら、止まらずに続けて読む(作業フォルダの外のテキストは、スキル `file-finder` の read コマンド。Word・Excel・PDF は `doc-convert`。多ければ `researcher`)。途中で聞くのは、結果が大きく変わる曖昧さがあるときだけ。

| 依頼 | 使うもの |
|---|---|
| ファイルを探す、「〜はどこ」、資料の 1 か所で答えが出る問い | `finder`(探して、読んで、答えまで返す) |
| 「〜について調べて」、Word・Excel・PowerPoint・PDF・長い文書を読む | `researcher`(探すところから任せる。先に `finder` を呼ばない) |
| 計算・単位の換算・判定(暗算しない) | `calc-check` |
| 手順書・マニュアル・長い資料を書く / 依頼が曖昧 | `doc-writing` / `interview` |
| 書いた文を整える | `yomiyasu`(長い文書は `polish`) |
| ノートに保存する・直す / 議事録 | `vault-notes` / `meeting-notes` |
| 図を作る / 図を読む | `diagram` / `diagram-reader` |
| タスク・期限、Git の差分、自作のアプリ | `app-ecosystem` |
| メール・予定 | `outlook`(受信と送信のキャッシュから探すので、期間や条件を聞き返さずに任せる) |
| 登場人物(自分も)を引く・覚える | `people`(覚えるのは `/people` のインタビューで) |
| Web を読む / Web の操作の自動化 | `browser` / `browser-session` |

## 読者と書き方

- 読者: 【例: 入社 1〜3 年目の作業者。現場で手順書を見ながら作業する】
- 文体: 【例: です・ます調。手順は「〜する」の言い切り】
- 用語: 【例: 社内の呼び方にそろえる。用語の表は docs/用語.md】
- 1 つの文書で 1 つの話題にする。結論を先に、理由と根拠を後に書く。

## 原典と根拠

- 原典(規格、社内基準、図面、過去の報告書、メール)の置き場: 【例: source/。Word・Excel・PDF のまま置く】
- 書く内容は、原典で確かめる。根拠は、文の近くか節の終わりに `出典: ファイルのパスとページ` で書く。根拠が無い文は書かない。分からないことは「未確認」と書く(推測で埋めない)。
- Word・Excel・PowerPoint・PDF の原典は、サブエージェント `researcher` に読ませる(直接は読めない)。原典を探すのは `finder`。
- 原典を書き換えない。原典の誤りに気づいたら、資料に書かずに報告する。
- AI が作ったノート・要約(未レビューのもの)は、根拠にしない。原典で確かめる。

## 資料の作り方

- 手順書・マニュアル・長い資料は、スキル `doc-writing` で書く(目次と用語の表を先に決め、承認を得てから、節ごとに根拠つきで書いて検査する)。
- 依頼の目的・読者・範囲が曖昧なときは、スキル `interview` で詰めてから書き始める。
- 書き上げた文章は、スキル `yomiyasu`(長い文書はサブエージェント `polish`)で、意味を変えずに推敲する。推敲の後に、数値・条件・出典が変わっていないかを確かめる。
- 図は、サブエージェント `diagram` で Excalidraw の図にする。既存の図を読むのは、スキル `diagram-reader`。
- 出力は Markdown。【例: 完成版は docs/ に置く。ファイル名は「番号_題名.md」】

## 数値と計算

- 数値(寸法、トルク、許容値、日付、数量)は、原典の値を使う。作り上げない。
- 計算・単位の換算は、暗算せず、スキル `calc-check` で検算してから書く。単位系: 【例: N、mm、MPa】
- 原典どうしで値が食い違うときは、どちらかに合わせず、両方の出典を示して確認する。

## 版と変更

- Git で管理する。変更の前に `git status` で状態を確認する。未コミットの変更は、勝手に戻さない・消さない。
- コミットは、頼まれたときだけ行う。`git push` と、履歴の書き換え(`reset --hard`、`rebase` など)はしない。
- 何が変わったかは、差分で見る(スキル `app-ecosystem` の `review` で、差分アプリの画面の URL を示す)。大きな改訂は、文書の終わりか `CHANGELOG.md` に、日付・変えたところ・理由を書く。
- レビュー・承認: 【例: 班長がレビューし、課長が承認する。承認前の版には「案」と書く】

## 構成

```
【例:

docs/       完成版の資料
drafts/     書きかけ
図/         Excalidraw の図】
```

## このプロジェクトで守ること

- 【例: 個人名・電話番号は書かない。役職で書く】
- 【例: 社外に出す資料は、社外秘の情報を含めない】

## サブエージェントの受け渡し用フォルダ

- サブエージェントが詳細を書く `.handoff/` は、このプロジェクトのルート直下にできる。使い捨てなので、Git には入れない。`.gitignore` に `.handoff/` が入っていることを確認する(なければ足す)。

## 確認が必要な操作

- 原典(source/ など)の書き換え・移動・削除
- 承認済みの完成版の上書き
- 社外への送付、メールの送信
