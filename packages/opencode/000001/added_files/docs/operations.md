# 運用メモ

## 1. 会社への持ち込み(myao-patch-bridge)

自宅の `opencode` リポジトリを myao-patch-bridge に登録し、会社の `%USERPROFILE%\.config\opencode` に適用します。

### 自宅側

- リポジトリは Git 管理にして、固定ブランチ(例: `main`)を決めて登録する。
- 公開前の「会社環境シミュレーション検証」が通ることを確認する。
- 名前の制約(Windows の予約名、使えない文字、末尾のピリオドなど)と、リポジトリ内の相対パス 156 文字以内の制約がある。スキルのフォルダ名を深くしすぎない。

### 会社側

- アプリ名は自宅のフォルダ名(`opencode`)と同じにする。
- `.config\opencode` は `000_work` の外にあるため、設定の `company_repo_paths` で対応付ける。

  ```json
  "company_repo_paths": {
    "opencode": "C:\\Users\\<ユーザー名>\\.config\\opencode"
  }
  ```

- 対象のフォルダは、Git リポジトリとして使える状態にしておく(初期化の要否は myao-patch-bridge の `docs/company-operation.md` で確認)。
- 適用前に未コミットの変更があると、自動で `[myao-patch] opencode update` としてコミットされる。

### 削除の扱い

パッチは削除の一覧も運び、会社側で削除されます。ZIP の上書きと違い、リポジトリで消したファイルが会社側に残る心配はありません。

## 2. 会社ごとの設定を守る

- 会社側の `opencode.json`(社内LLMの設定)は `.gitignore` で管理から外している。パッチで上書きされず、自動コミットにも入らない。
- 配布するのは `sample_opencode.json` だけ。変更があったら、会社の `opencode.json` と見比べて、必要な箇所を手で反映する。
- `sample_opencode.json` にはプロバイダ(社内LLM)の設定を入れていない。
- OpenCode が自動で作る `node_modules/`、`package.json`、ロックファイルも管理から外している。

## 2.2 会社の環境の前提と、ハーネスの部品の方針

| 項目 | 会社の環境 | ハーネスでの扱い |
|---|---|---|
| Python | 使える。PATH が通っている | 補助スクリプトは Python で書く |
| `pip install` | 使える。接続先は PyPI(ミラーではない。ミラーにすることを推奨されている) | 標準ライブラリで足りるなら使わない。入れるときは、`requirements.in` などに記録する。下の「pip の扱い」も参照 |
| Node.js | 最新版が入っている | 自分で書くスクリプトは、標準モジュールだけ。例外: 自宅で取得して同梱した依存(Playwright MCP。[docs/mcp.md](mcp.md)) |
| `npm install` / `npx` | パッケージを取得できない | `sample_opencode.json` で `deny`。`npx` で起動する MCP サーバーは使えないので、依存ごと同梱して `node` で直接動かす |
| インターネット | 直接は接続できない | 外部の API や MCP サーバーに頼る部品は入れない |

部品を足すときの方針:

- **補助スクリプトは、Python の標準ライブラリだけで書く。** スキル専用のものは、そのスキルのフォルダの `scripts/` に置き、`run.bat` を入口にして、スキルの手順から呼び出す(例: `skills/outlook-mail/`、`skills/file-finder/`、`skills/doc-convert/`、`skills/handoff-clean/`)。依存パッケージが要るものは、リポジトリ直下の `requirements.in` と、ハッシュ付きの `requirements.lock`(myao-patch-bridge と同じ方式)で管理し、**ハーネスのフォルダ直下の `.venv`** に入れる(下の「pip の扱い」)。テストは偽の相手(偽の Outlook、偽のサーバー)で書き、自宅で通してから運ぶ。
- **MCP サーバーは、依存ごと同梱できるものだけ。** Node.js のサーバーは、自宅で `node_modules` ごと取得して `mcp/<名前>/` に入れ、`node` で直接動かす(Playwright MCP)。Python のサーバーは `pip install`(`requirements.lock`)で入れる。`npx` で起動するものは使えない。詳細は [docs/mcp.md](mcp.md)。
- **OpenCode のカスタムツール(`tools/`)とプラグイン(`plugins/`)は、会社では使わない前提にする。** これらは OpenCode 用のパッケージを取得する必要がある可能性があるが、公式ドキュメントで確認していない。必要になったら、会社で小さく試してから決める。
- **ビルドが要るもの(フロントエンドなど)は、自宅でビルドして、成果物を Git で運ぶ。** myao-patch-bridge など、会社へ運ぶ既存のアプリで、すでにこの方式(`dist/` を Git 管理)を取っている。

### pip の扱い(PyPI へ直接つなぐ間)

PyPI へ直接つなぐ間は、悪意のあるパッケージや、似た名前のパッケージを入れてしまう危険がある。LLM が実在しない名前を思いついて、そのまま入れてしまうことにも注意する。

- **プロジェクトごとに `.venv/` を使う。** ハーネス自身のスクリプト(Outlook、ファイル検索、文書の変換)が使う `.venv` は、ハーネスのフォルダ(`C:\Users\<ユーザー>\.config\opencode\`)の直下に 1 つだけ作る(`run.bat` がここを探す)。本体の Python にはパッケージを入れない。`python -m venv .venv` で作り、`.venv\Scripts\python`(Windows)のように、venv の Python を直接指定して実行する(有効化の操作は不要)。`.venv/` は Git に入れない。myao-patch-bridge の `install_company.bat` も、`.venv` を作れる環境ではこの方式。
- `sample_opencode.json` の `"*pip install*": "ask"` は、`.venv\Scripts\python -m pip install ...` のような形にも一致する。
- 入れるパッケージは、人間が決める。LLM には、`requirements` にあるものか、指定された名前のものだけを入れさせる(`AGENTS.md` に書いてある)。
- バージョンは固定する。可能なら、ハッシュ付きの `requirements.lock` を作り、`pip install --require-hashes -r requirements.lock` で入れる。myao-patch-bridge の `install_company.bat` と同じ方式。
- **リポジトリには、接続先の URL を書かない。** 接続先は、会社の PC の `pip.ini`(`%APPDATA%\pip\pip.ini`)か、環境変数 `PIP_INDEX_URL` で決める。ミラーに切り替わったときは、この設定だけを変えればよく、リポジトリは変更しなくて済む。
- ミラーが入るまでは、入れたパッケージの名前とバージョンを、`requirements.in` で一覧できるようにしておく。
- **いま入っているもの:** `pywin32`(Outlook。Windows 用)、`pypdf`(PDF の変換。標準ライブラリだけでは PDF を読めないため。依存は `typing-extensions` だけ)。どちらも、無くても他の機能は動く(`pypdf` が無いと PDF だけ変換できない)。

## 2.3 サブエージェントの設計(コンテキストの節約)

### 狙い

メインエージェントのコンテキストを節約しながら、良い答えを得る。節約の本体は、**子セッションが分離されていること**にある。子の中間の読み取りや検索の結果は、メインに入らない。メインに入るのは、子の返答だけ。(公式ドキュメントは、子が「fresh context」で動くと書いている。返答だけが親に戻るかは明記されていないため、会社で確認する)

### 節約と品質のバランス

- **返答が短いほど節約になるが、短すぎると情報が欠けて、回答の質が下がる。** そのため、返答には「結論・根拠(パス:行)・確信度・未確認」を必ず含める。
- メインは、判断の決め手になる事実を、根拠のパスを開いて自分で確認する。すべては読まない。
- **返答が不足しているとき**(確信度が中・低、答えに関わる未確認がある、根拠が足りない)は、メインが補う。詳細ファイルがあれば読み、なければ同じ子に続きを依頼するか、範囲を絞って任せ直す。この規則は共通 `AGENTS.md` にある。社内LLMが実際にそう動くかは、会社で確認する(測り方のテストに、確信度が低くなる質問を 1 つ入れる)。
- 子の要約が間違っていても、根拠を見れば気づける形にしておく。

### いつ子に任せるか(固定コストがあるため)

子セッションの起動には、システムプロンプトなどの読み込みという固定のコストがかかる。

| 任せる | 自分でやる |
|---|---|
| 5 つ以上のファイルや長い文書を読む調査 | 1〜2 ファイルの読み取り |
| 互いに独立した調査 | 数行の編集 |
| 結果が要約で足りる作業 | ユーザーと確認しながら進める作業 |

この基準は、共通 `AGENTS.md` に書いてある。

### 部品

| 部品 | 役割 |
|---|---|
| `agents/researcher.md` | 大量のファイルを読んで、問いに根拠つきで答える。節約効果が最も大きい。Vault のノート検索にも使う |
| `agents/reviewer.md` | 読み取り専用のレビュー |
| `agents/outlook.md` | Outlook のメール・予定・フォルダを、スキル `outlook-mail` のスクリプトで扱う。メールの整理(フォルダの作成と移動)は、案 → 承認 → 実行の順。メールは文章量が多いので、子で処理して要約だけを返す([docs/outlook.md](outlook.md)) |
| `agents/browser.md` | ブラウザ(Playwright MCP)で社内の Web ページを読む。ページの内容は文章量が多く、MCP のツール定義も大きい(約 2.1 万文字)ので、メインには持たせず、この子だけに持たせる([docs/mcp.md](mcp.md)) |
| `agents/researcher.md` + スキル `doc-convert` | Word・Excel・PowerPoint・PDF を Markdown に変換してから読む(`read` では読めないため)。画面には保存先と目次だけを出し、必要な部分だけを読ませる([docs/convert.md](convert.md)) |
| `agents/obsidian.md` + スキル `obsidian-run` | Obsidian のコマンドを、許可リストにあるものだけ実行し、できたファイルを知らせる。実行結果は返らないので、前後のフォルダの差で検出する([docs/obsidian.md](obsidian.md)) |
| `skills/vault-notes/`、`commands/save-note.md`、`commands/fix-note.md` | ノートの保存(今日のフォルダー)と修正(バックアップ → 承認 → 最小の変更)。メインが行う |
| `agents/diagram.md` + スキル `excalidraw-diagram` | Excalidraw の図を、仕様から作り、点検する。読み戻しは、`diagram-reader` を使う。[docs/excalidraw.md](excalidraw.md) |
| スキル `diagram-reader`、`commands/read-diagram.md` | 図(Excalidraw・draw.io)を、画像を見なくても分かる文章にして読む。`researcher` と `diagram` が使い、`describe` はメインからも確認なしで使える(画像が見られない環境のため)。[docs/diagram-reader.md](diagram-reader.md) |
| `agents/finder.md` | ローカルのファイルを、中身(Local-fulltext-search)と名前(Everything)で探して、パスと根拠の抜粋だけを返す。検索してよい場所は設定のフォルダだけ。中身を読む作業は `researcher`([docs/search.md](search.md)) |
| `commands/summarize.md` | `subagent: true` で子セッションとして実行する。大きなファイルの要約が、メインに入らない |
| `skills/handoff-clean/`、`commands/handoff-clean.md` | `.handoff/` の古いファイルを、`_trash` へ退避する(削除はしない)。メインが、一覧を見せて承認を得てから行う。サブエージェントには持たせない |
| `skills/create-subagent/` | 新しいサブエージェントを作る手順と、返し方の約束の原本(`handoff-block.md`) |
| `skills/project-init/`、`commands/init-project.md` | プロジェクトのフォルダに、`AGENTS.md`(汎用テンプレートから)、`.handoff/`、`.gitignore` の行を置く。上書き・削除はしない。`.git` が無ければ `git init` も行う(コミットはしない)。メインが行い、`apply` と `git init` は承認の後([docs/project-init.md](project-init.md)) |
| `skills/app-ecosystem/`、`commands/apps.md` | 自作の Web アプリ(ガント・ファイルマネージャー・差分・Excalidraw・全文検索)を、各アプリの共通の入口(エコシステム API 1)で使う。読み取りと試行は確認なし、書き込みは `--dry-run` → 承認。削除・コマンドの実行は持たない。出力が小さいので、メインが行う([docs/apps.md](apps.md)) |
| `agents/polish.md` + スキル `yomiyasu`(同梱)、`commands/polish.md` | AI が書いた日本語の文書を、意味を変えずに推敲する。手順書は約 4,500 文字の要約版(元の約 4.3 万文字は `references/upstream-SKILL.md`)。短い文はメインで、長い文書やファイルは子セッションで推敲する(メインには最終稿のパスと要点だけが戻る)(`skills/yomiyasu/VENDOR.md`) |

組み込みの `explore`(読み取り専用の探索)と `general` もある。自作の `researcher` は、返し方の約束を持たせるために別名で作っている。組み込みと同名のファイルを置くと上書きになるが、置き換えか統合かはドキュメントに書かれていないため、同名では作らない。

### 返し方(`.handoff/`)

- **短いとき(目安 15 行以内)は、返答に直接書く。ファイルは作らない。** ファイルを書いて読むと、かえってコストがかかる。
- **長いときだけ、** 作業フォルダ直下の `.handoff/エージェント名_話題.md` に詳細を書き、返答は短くする。
- **場所:** ハーネスのリポジトリには置かない(置くと、myao-patch-bridge の自動コミットに入る)。各プロジェクトの `.gitignore` に `.handoff/` を入れる(テンプレートに注意書きがある)。ドットで始まるので、Obsidian の検索やインデックスの対象外になる。
- **ファイル名:** 日時を入れない(サブエージェントは現在時刻を知らないことがある)。同名があれば `_2`、`_3`。
- **掃除:** 使い捨て。`/handoff-clean` で、古いものを `.handoff/_trash/<日時>/` へ**移動**する(まず一覧を見せ、承認を得てから実行。`--dry-run` で対象を確認できる)。**削除する機能は無い。** `_trash` の中身を消すのは人間(エクスプローラーで削除)。移動の記録(`<日時>.manifest.txt`)が残るので、戻せる。`.handoff/converted/`(変換結果)と `.handoff/playwright/`(ブラウザの出力)も同じ扱い。
- **権限:** 読み取り専用のエージェントにも、`.handoff/**` への書き込みだけを許可する。
- **上限:** サブエージェントには `steps`(20〜25)を付ける。社内LLMが同じ操作を繰り返して、トークンを使い続けるのを防ぐ。上限に達すると、まとめを書いて終わる。

### 効果の測り方(会社で行う)

コンセプトが正しいかは、測らないと分からない。同じ質問を 2 通りで試して比べる。

1. **メインだけで調べる。** 例: Vault から「〇〇について書いたノートを探して、要点をまとめて」。
2. **`researcher` に任せる。** 同じ質問を、`researcher` を使って調べさせる。

比べるもの:

- メインのコンテキスト使用量(OpenCode の画面に出るトークン数)
- 回答の正しさ(根拠のパスが実在するか、要点が欠けていないか)
- かかった時間

子に任せた方が、使用量が下がり、回答の質が同じなら成功。質が下がるなら、返答の形(根拠の件数など)を見直す。小さな質問では、メインだけの方が速くて安いはず。それを確認して、基準の数字(5 ファイル)を調整する。

### 会社で確認すること(未確認)

- 子の返答だけが親に戻るか(中間の出力が親のコンテキストに入らないか)。
- 子が、共通 `AGENTS.md` を読むか。公式ドキュメントには書かれていない。読む場合は、その分の固定コストがかかる。読まない場合でも、各エージェントの本文に約束を入れてあるので動く。
- `edit` の権限で `".handoff/**"` のようなパスの指定が効くか。パスの基準が作業フォルダか、`~/.config/opencode` かも確認する。
- `subagent: true` のコマンドが、`researcher` で動くか。
- Claudian 経由でも、サブエージェントが動くか。
- 社内LLMが、指定の形で返答できるか。呼び出しの判断(`description` を見て呼ぶか)が妥当か。

### スキルとスラッシュコマンド

- スキル(`skills/`)は、スラッシュコマンドでは呼び出せない(公式ドキュメントに記述がない)。モデルが、名前と `description` を見て、`skill` ツールで読み込むかを決める。
- スラッシュコマンドは `commands/名前.md` で作る。人が呼び出したいスキルには、同じ名前のコマンドを作り、本文で「スキル〇〇を読み込み、その手順に従う」と指示する。
- 現在の対応: `/meeting-notes` → スキル `meeting-notes`、`/create-subagent` → スキル `create-subagent`。`python-env` はモデルが使うものなので、コマンドは作らない。
- 本文でスキルを指示する方法は、公式ドキュメントに書かれていない。会社で、スキルが実際に読み込まれるかを確認する(機能テストに追加)。読み込めないときは、コマンド本文に手順を直接書く形に変える。
- 新しい版では、プロンプトに `@スキル名` と書いて読み込ませる方法がある。会社の版で使えるかは未確認。

## 2.4 常時読み込まれるものの大きさ

`AGENTS.md` は、すべてのセッションの先頭で読み込まれる(子も読む可能性がある)。大きいほど、毎回のコストが上がる。

- **0.20.0 で、共通 `AGENTS.md` を「すべての作業に共通すること」だけにした(2,471 文字。上限 2,500)。** 利用者の依頼と、公開の指針(毎回読み込まれるので小さく保ち、細部はプロジェクトのファイルやスキルに分ける。[aihero.dev のガイド](https://aihero.dev/a-complete-guide-to-agents-md)、[Thoughtworks の Agent instruction bloat](https://www.thoughtworks.com/radar/techniques/agent-instruction-bloat))に合わせた。スキルとエージェントの対応表は、一般資料と Obsidian のテンプレートへ移し、共通には、スキルの探し方(プロジェクトに無ければ `~/.config/opencode/` を見る)と、「人・案件・手続きは答える前に `finder` で探す」の 1 行だけを残した。Python と Node.js の決まりは、coding のテンプレートとスキル `python-env` へ移した。
- (0.20.0 より前)共通 `AGENTS.md` は、約 2,300 文字(約 6 KB)。最初の版から約 3 割減らしたあと、サブエージェントの任せ先と安全のルールを足した。整合性テストが、2,500 文字を超えないことを検査する。日本語のトークン数は、文字数の 1〜2 倍が目安(モデルによる)。詳細な手順は、必要なときだけ読み込まれるスキル(`python-env`)に移した。まだ減らす余地はあるが、安全のルールは常に効かせたいので、これ以上は削らない。
- プロジェクトや Vault の `AGENTS.md`(テンプレートからコピーしたもの)も、同じ扱いで読み込まれる。使わない節は消す。
- スキルは、名前と説明だけが常に見える。本文は、使うときだけ読み込まれる。

## 2.5 AGENTS.md の分け方

| 置き場所 | 役割 | 内容 |
|---|---|---|
| `~/.config/opencode/AGENTS.md`(このリポジトリの `AGENTS.md`) | 全フォルダに効く共通ルール | どこでも成り立つ最小限のルール(スキルの探し方を含む。使い分けの表は書かない) |
| 各プロジェクトのルートの `AGENTS.md` | プロジェクト用(プログラム・設計計算・CAE か、一般資料。Git 前提) | `/init-project` が、中身とインタビューで `templates/project/coding/` か `document/` の AGENTS.md` から置く(手でコピーしてもよい)。【 】を書き換える。[project-init.md](project-init.md) |
| Vault のルートの `AGENTS.md` | Obsidian 用 | `templates/obsidian/AGENTS.md` をコピーして書き換える |

- 共通とフォルダ別は、設定のようにマージされるのではなく、文章として連結されて LLM に渡される。矛盾する指示を書かない。フォルダ別には、共通ルールへの「書き足し」だけを書く。
- 同じ種類の中では、作業フォルダから上にたどって最初に見つかった 1 つだけが使われる。サブフォルダに置くと、親フォルダの `AGENTS.md` は読まれなくなる。
- 新しいプロジェクトの正本は `AGENTS.md` に一本化する(二重管理を避ける)。
- **以前 Claude Code で開発したリポジトリには、`CLAUDE.md` がある。** OpenCode は、プロジェクトに `AGENTS.md` があると `CLAUDE.md` を読み込まない(公式の rules ページ。V2 の移行ページには「`AGENTS.md` のみを探索」ともあり、版で扱いが違う可能性がある)。そこで、共通ルール(`AGENTS.md` の「基本」)に「作業フォルダに `CLAUDE.md` があれば、最初に読む」と書いた。子には、関係する規則を依頼文に書いて渡す(子は履歴を見られず、共通 `AGENTS.md` を読むかも未確認のため)。
- 既存のプロジェクトでは、すでにある `AGENTS.md`(仕様書を兼ねているものが多い)に、テンプレートの「作業の進め方」の節を足す形が現実的。

## 4. OpenCode の仕様メモ(2026-11-07 時点の公式ドキュメントに基づく)

> **V2 の書き方に合わせている。** 利用者が OpenCode V2 を使っているため、設定・エージェント・コマンドを V2 の書き方にした(2026-11-07)。V1 の旧名は V2 でも読まれるが、**1 つのファイルの中で新旧を混ぜると、旧名の項目は無視される**(公式の移行ページ)。V1 の OpenCode には使えない。会社の版は記録しておく([company-checklist.md](company-checklist.md))。

V1 から変えたところ(公式の移行ページと設定ページに基づく):

| V1(旧) | V2(現在) |
|---|---|
| `permission`(ツール別の対応表) | `permissions`(`action`・`resource`・`effect` の配列。最後に一致したルールが勝つ) |
| `bash`、`task` | `shell`、`subagent` |
| `autoupdate: false` | `update: "disable"`(公式に対応表はなく、スキーマの説明からの推定) |
| `mcp.<名前>`、`enabled: false`、`timeout: 60000` | `mcp.servers.<名前>`、`disabled: true`、`timeout: {startup, catalog}`(ミリ秒) |
| コマンドの `subtask: true` | `subagent: true`(`subtask` は別名として受け付けられるが、使わない) |

- 雛形で変えた挙動の補い: V2 では `external_directory` が既定で許可。雛形で `ask` を明示した。`.env` の読み取りは、V2 の基本ポリシーでは確認だが、後ろの `read` の許可で打ち消されるため、雛形で `read` の後ろに明示した(順序はテストが検査)。
- MCP は `codemode: false` にした。V2 の既定の Code Mode では、ツールが `execute` 経由で呼ばれる。ツール単位の権限(`browser` の `playwright_*`)が Code Mode でも効くかは、公式に記載がなかったため、V1 と同じ「ツールをそのまま見せる」形にした。
- グローバルの `~/.config/opencode/AGENTS.md` は、すべてのセッションに効く。プロジェクトの `AGENTS.md` があれば、両方が合わさる。`CLAUDE.md` への代替読み込みは、移行ページには「V2 は AGENTS.md のみ」とあるが、rules ページには CLAUDE.md の読み込みも書かれていて、食い違う(このハーネスは AGENTS.md だけを使うので影響しない)。
- サブフォルダ名は複数形(`agents/`、`commands/`、`skills/`)が現行。単数形も互換のために読まれる。
- 設定ファイルは置き換えではなく**マージ**される。優先順位は、グローバル → `OPENCODE_CONFIG` で指した別ファイル → プロジェクトの `opencode.json` の順で、後のものが勝つ。
- `permissions` の `effect` は `allow` / `ask` / `deny`。`shell` の `resource` はコマンド文字列に対するパターンで、`*` は `/` を含む任意の文字列、末尾が ` *` なら引数なしにも一致する。**後ろに書いたものが優先**される。複合コマンドは、部分ごとに判定される。
- **判定の細部(2026-11-07、Mac の v2.2.6 のバイナリの中のコードを読んで確認。公式の permissions ページとも一致):** ルールは「基本(すべて許可、`.env` は確認)→ グローバル → エージェント」の順に連結され、最後に一致したものが勝つ(一致なしは `ask`)。パターンは**全体一致**で、`\` は `/` に直してから比べる(Windows では大文字小文字を区別しない)。複合コマンド(`&&`、`;`、`|`)は部分ごとに判定されるが、**リダイレクト(`> ファイル`)は、その部分の文字列に含まれたまま**判定される。シェルを解析できないコマンドは、実行されずにエラーになる。整合性テスト(`PermissionBehaviorTests`)が、この判定を写して、実際のコマンドで許可・確認・拒否を確かめる。
- **0.16.0 で、確認を「本当に危険なもの」に絞った**(利用者の依頼「許可が煩雑で使いにくい。Claude Code と同じ使用感に」。作業はほぼ Git で管理しているため)。メインは、`shell` と `edit` が既定で許可。確認は、Git で戻せない操作(`rm`・`del`・`rd`・`Remove-Item`、`git push`・`reset --hard`・`clean`・`checkout --`・`checkout .`・`restore`・`stash drop`/`clear`・`branch -D`)、パッケージの導入・削除(`pip`)、本番のデータベースの書き込み(`app-ecosystem` の `task-add`/`task-update`/`task-link`。`--dry-run` は許可)、送信を許すブラウザの実行(`--allow-submit`)、作業フォルダの外(`external_directory`)、`.env` の読み取りだけ。スキルの読み込み(`skill`)も、明示的に許可した。拒否は、外への通信(`curl`・`Invoke-WebRequest` など)、`npm install`・`npx`、強制の push、`format`・`diskpart`。複合コマンドは部分ごとに判定されるので、`cd x && rm y` の `rm` も確認になる。サブエージェントは、役割を絞るため、これまでどおり `shell` を既定で拒否する(子の確認は、Outlook の書き込みと予定の作成だけ)。`python -c` の中の削除のように、パターンで捕まえられない操作はある(Claude Code と同じ)。
- **0.22.0 で、抜けを塞ぎ、二重の確認を減らした**(経緯は README の 6.30)。確認に足したもの: メインから直接呼ぶ Outlook の書き込み(`cal-create`・`folder-create`・`mail-move`・`mail-undo`。`--dry-run` は許可)、履歴の書き換え(`git rebase`・`commit --amend`・`filter-branch`・`reflog expire`)、`git checkout <版> -- ファイル`・`git switch --discard-changes`、`find -delete`・`find -exec rm`、シェルでの `.env` の読み取り(`.env.example` は許可)、`.env` の編集、秘密鍵らしいファイルの読み取り(`*.pem`・`*.key`・`*.pfx`・`*.p12`・`*.kdbx`・`id_rsa`・`id_ed25519`)、`ssh`・`scp`・`sftp`・`ftp`、`reg add`・`reg delete`・`Set-ExecutionPolicy`、`pip download`。拒否に足したもの: 位置を問わない強制の push(`--force`・`-f`・`+ブランチ`)、`curl.exe`・`wget.exe`、コマンドの途中にある `Invoke-WebRequest`・`Invoke-RestMethod`・`Net.WebClient`・`DownloadFile`・`DownloadString`、`Start-BitsTransfer`・`bitsadmin`・`certutil -urlcache`、`-EncodedCommand`、`Format-Volume`・`Clear-Disk`。子は、全部、別の子を呼べず(`subagent` を拒否)、役割のスキルだけを読み込める。`reviewer` だけは、Git の読み取り(`git status`・`diff`・`log`・`show`。`--output` と `>` は拒否)ができる。
- **以下は 0.9.0〜0.15.0 の書き方(メインの `shell` が既定で確認だったころ)。サブエージェントには今も当てはまる:**
  - 許可したコマンド(`type`、`dir`、`git log` など)でも、`>` でファイルに書けてしまう(`type nul > main.py` でファイルが空になる)。雛形は、許可の後ろに `*>*` の `ask` を置く。サブエージェントは `*>*` を `deny`(書くのは `--out` で `.handoff/` の中だけ)。`git diff` / `git log` の `--output` も `ask`。
  - パターンは、コマンドのどこに一致してもよい。書き込みの `ask` は、読み取りの `allow` より**後ろ**に置く(先に置くと、件名やファイル名に `mail-list` などを含むだけで、確認が打ち消される)。` --dry-run` の許可は、前に空白を入れる。
  - スキルのパスを引用符で囲む(`"C:\…\run.bat" today`)と、`run.bat today` の形の許可に一致しない。そのときは確認になる(危険側には倒れない)。
- **0.10.1 で足した許可:** メインも `.handoff/**` には確認なしで書ける(下書きと仕様の置き場。使い捨て)。スキルのフォルダ `~/.config/opencode/skills/**` は確認なしで読める(`~` は、設定の読み込み時にホームへ展開される)。`run.bat … --help` は、末尾が `--help` のときだけ確認なし。`opencode run`(対話なし)では、確認が要る操作はすべて自動で拒否されるので、書き込みは対話の画面で行う。
- **会社の Windows で、OpenCode がどのシェルを使うかは未確認。** 公式の V2 ドキュメントに記載がない(解析できるのは Bash・Zsh・POSIX sh・PowerShell と書かれている。cmd の記載はない)。チェックリストの 2 で確かめる。
- `share` は、公開スキーマで `manual` / `auto` / `disabled` を確認した(`disabled` で共有を無効にできる)。
- ドキュメントで確認できなかった項目: モデル一覧の取得を止める方法、テレメトリの停止方法。会社の版では、外部への通信がないかを社内のセキュリティ部門に確認する(手順書 5-E)。

調査: Anthropic の公式記事(コンテキスト設計、ツール設計、マルチエージェント、スキル、長時間タスクのハーネス、評価)、OpenCode の公式ドキュメント、実務者の記事を読み、今の構成と照らした。**構成は、世の中の定石とおおむね一致していた**(短い常時の指示、スキルの段階的開示、サブエージェントによる文脈の分離と `.handoff/`、狭い許可リスト、失敗のたびにテストを足す)。経緯と出典は [README.md](../README.md) の 6.14。足りなかった点を、次の運用のルールにする。

### 5.1 指示に行を足す基準

- `AGENTS.md`、エージェント、スキルに規則を足すのは、**実際に起きた失敗に結び付くときだけ**。先に大量に書かない。足したら、[CHANGELOG.md](../CHANGELOG.md) に、何が起きたかを一言書く。
- 守らせたい規則は、可能なら、指示文だけにせず、許可ルールやスクリプトの制限、テストでも守らせる。指示文は「ほぼ毎回」しか守られない(フックについては 5.6)。
- 上限(`AGENTS.md` 2,500 文字、description の合計 2500 文字)は、増やすときに何かを外す。
- **モデルや OpenCode の版が変わったら、規則と部品を見直す。** どの部品も「モデルにできないこと」の仮定を含み、モデルの更新で不要になることがある。見直しは、**1 つずつ外して**結果が変わらないかを確かめる(一度に大きく削ると、効いていたものが分からなくなる)。

### 5.2 効果の測定(会社で行う)

[company-checklist.md](company-checklist.md) の 15 を、次の形で行う。

- 依頼を 20〜50 件集める。**実際に困った依頼**から選ぶ。小さく始めてよい。
- **「子に任せるべき依頼」と「任せるべきでない依頼」(1〜2 ファイルを読むだけ)の両方**を入れる。片方だけだと、一方向に偏る。
- 各依頼で、成否、メインのトークン数、時間、**スキルやサブエージェントが呼ばれたか**を記録する。呼ばれるべき依頼で呼ばれない割合が、高ければ、`description` と `AGENTS.md` の案内を直す。
- 結果は毎回変わるので、同じ依頼を数回繰り返す。
- 失敗は、記録を読んで、ハーネスの問題か、依頼や判定の問題かに分ける。
- 小さな依頼で、子を使うほうが遅く高いなら、`AGENTS.md` の「5 ファイル」の基準を上げる。

### 5.3 想定モデル(Inkling-Small)に関して見ること

公式の資料と、このハーネスの関係は [README.md](../README.md) の 3。会社で測るとき(5.2)に、次を見る。

- **長い会話**: 公式に「長い多ターンの会話で性能が落ちることがある」とある。1 つのセッションで、どこから質が落ちるかを記録する(落ちるなら、`AGENTS.md` に「長くなったら、要点をファイルに残して新しいセッションを始める」を足す。実際に落ちたときだけ)。
- **事実の想起が弱い**: 読んでいない内容を、記憶で答えていないか。答えに根拠のパスがあるか。
- **指示への追従**: `AGENTS.md` の規則(「変更の前に 1〜2 行で示す」「削除は確認する」など)が、守られているか。守られない規則は、指示文を強めるのではなく、許可ルールやスクリプトの制限で守らせる。
- **思考の深さ**: 切り替え方は公式に記載がない。会社で切り替えられるなら、調べるだけの子(`researcher`、`finder`)は浅く、設計や判断は深く、の使い分けを試す。
- **多段の承認**: `outlook`(案 → 承認 → 実行)と `/fix-note`(バックアップ → 承認 → 変更)が、最後まで正しく進むか。
- **コンテキストの上限(約 13 万)**: 次の 5.4 の確認項目を行う。

### 5.4 コンテキストの上限(約 13 万)と、プロバイダーの設定

会社の配備は、コンテキストが約 13 万トークンに制限されている(利用者の申告。出力の上限は約 8 万と記憶しているが未確認)。公式の「最大 1M」とは別の制限で、窓の小ささが、設計に効く。

**最重要: 会社側の `opencode.json` の、モデルの定義に `limit` を書く。** OpenCode V2 の公式ドキュメント(モデルのページ)によると、カタログにないモデルで `limit` を省略すると、**コンテキスト 20 万・出力 3.2 万と仮定される**(検出されない、ただの仮定)。実際の窓が 13 万だと、自動圧縮が遅れ、窓を超えて拒否される恐れがある(拒否されたときは、圧縮して 1 回だけ再試行する安全網はある)。このリポジトリの `sample_opencode.json` には、会社固有のプロバイダーの設定を入れないので、会社側で次の形を確かめる。

```jsonc
"providers": {
  "<プロバイダーID>": {
    "models": {
      "<モデルのキー>": {
        "limit": { "context": 130000, "output": 32000 }
      }
    }
  }
}
```

- V2 の書き方(`providers`)。V1 の `provider` で書いてある場合も、`models` の中に同じ意味の `limit`(`context`、`output`)がある。**確認するのは、`limit` が書かれているか。**
- `context` は、実際の窓(約 13 万)以下にする。単位は、公式に明記がないが、"token limits" とある(トークンとして扱う)。
- `output` は、小さめから始める(上の例は 3.2 万)。公式に、`limit.output` が送信時の最大出力に使われるかの記載がない。サーバーが「入力 + 最大出力 ≤ 窓」を検査する場合、出力を大きく書く(8 万など)と、長い入力が拒否される恐れがある。実測して、足りなければ上げる(**この助言は、私の判断で、公式の記載ではない**)。
- 圧縮の設定(`compaction`)は、既定で「窓の 15% を空けた時点で自動圧縮」「直近 15,000 トークンを残す」。窓が 13 万だと、約 11 万で圧縮が始まる。頻繁に圧縮されて質が落ちるなら、`buffer` や `keep.tokens` を調整する(実測してから)。

**このハーネスで、窓の小ささに効く点:**

- `read` は、公式の仕様で、1 ページが 2,000 行・50 KiB まで(1 行は 2,000 文字で短縮)。日本語(UTF-8)で 50 KiB は、おおよそ数万トークンになりうる。1 回の `read` で窓の数割を使う恐れがあるので、大きなファイルは `offset` と `limit` で部分的に読む(`doc-convert` は、目次の行番号で読む設計)。
- 長い文書や多数のファイルは、子(`researcher`)に任せる。子の窓も 13 万なので、1 つの子に多くを読ませすぎない(`steps` は 20〜40)。
- `describe` は、既定で 220 行まで(`--max-lines`)。`doc-convert` は、本文を画面に出さない。長い結果は `.handoff/` に置く。

**会社で確認すること:**

- [ ] 会社側の `opencode.json` に、モデルの `limit` が書かれているか。
- [ ] 長い文書(目次つきの変換結果)を読ませて、圧縮が働くか。窓を超えて拒否されないか。
- [ ] `browser` で、大きなページのスナップショットが窓に収まるか。
- [ ] `outlook` で、長いメール本文を読んでも収まるか。

### 5.6 フック(プラグイン)と policies(2026-11-07 に公式ドキュメントで確認)

「ツール実行の前後に処理を差し込む」ものは、OpenCode V2 にある。ただし、**いまのハーネスには入れていない。**

**あるもの**

- **プラグインのフック**(コードで書く。TypeScript / JavaScript)。V2 のフック: ツール実行の前後(`tool.execute.before` / `after`)、権限の判定(`permission` の `evaluate`)、シェルコマンドの作成前(`shell` の `create.before`)、セッションの入力・モデル呼び出し前・コンパクション前、HTTP の送受信、など。置き場所は `~/.config/opencode/plugins/`(またはプロジェクトの `.opencode/plugins/`)。設定の `plugins` でも宣言できる。
- **`policies`**(設定に書く。コードは要らない)。権限のルールと保存済みの承認の**後に**、`deny` を強制する(`allow` を与えることはできない)。例: `{"action": "tool.use", "resource": "shell:git push *", "effect": "deny"}`。グローバルや管理用の policy は、プロジェクトの設定より優先される。

**ないもの・分からないもの**

- 「セッション終了時にテストが通るまで止める」(Claude Code の Stop フックのような)、「ファイル編集後に自動で実行する」専用のフックは、V2 の公式で名前が確認できなかった。
- `tool.execute.before` で、実行を**止める**書き方は、公式に記載がなかった(権限フックの `deny` と、`permission.assert` の拒否は記載あり)。`execute.after` で、リンターを走らせて結果に載せる例も記載なし。
- プラグインの実行環境(Bun か Node か)、1 ファイルだけで動くか、npm の取得が要るか(**オフラインで使えるか**)は、記載なし。
- V1 のプラグインは V2 では動かない(V1 のフックは V2 に変換されない)。

**判断(私の意見。公式の記載ではない)**

- **いまは入れない。** 理由: (1) 守らせたいことの大部分は、許可ルール、スクリプトの制限、テストで、すでに決定的に守らせている。(2) 公式に記載のない点(止める書き方、実行環境、オフライン)が、会社で使えるかを左右する。(3) プラグインは任意のコードを実行できるので、会社のセキュリティ部門への確認(チェックリストの 16)が増える。このハーネスの方針(Node は標準モジュールだけ、新しい仕組みを入れない)とも合わない。
- **入れるなら、最初は `policies`。** コードが要らず、`git push`、`rm`、`curl`、`npm install` などの拒否を、プロジェクトの設定に緩められない形で強制できる。今は `permissions` の `deny` で同じ効果があり、緩められるのは書き換えた人だけ(会社側の `opencode.json` を直す人)。**本当に困ってから**入れる(5.1 の基準)。
- 次に検討するのは、プラグインの `permission` の `evaluate`(拒否の追加)。「編集のたびにテスト」「完了前にテスト」は、公式のフックだけでは実現できるか未確認。
