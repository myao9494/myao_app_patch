# プロジェクトの初期設定(`project-init`)

スキル `project-init` とコマンド `/init-project` の設計。使い方は [skills/project-init/SKILL.md](../skills/project-init/SKILL.md)。

## 1. 目的と、最初に決めたこと

- 新しいプロジェクト(フォルダ)で、このハーネスを使うために必要な最小のファイルを、**人間が手でコピーして書き換えるのをやめ**、確認してから自動で置く。手作業では、コピーを忘れる、`.gitignore` への追記を忘れる、既存の `AGENTS.md` を上書きする、といった事故が起きやすい。
- 対象は、**プログラムだけでなく、設計計算、構造計算、CAE のモデルなどを扱うリポジトリ**(ユーザーの依頼)。ただし Python のコードはほとんどの場合に出てくるので、Python の決まりは残す。
- **Git で管理する前提**。
- **Obsidian の Vault は対象外**(Vault は、人間がテンプレートを配置する)。
- 方式は、LLM に判断させる手順書ではなく、**スクリプトに置く内容を決めさせる**。LLM は、どのフォルダかを確かめ、結果を人間に見せるだけにする(上書きや範囲の逸脱を、LLM の判断に任せない)。

## 2. 構成

```
スキル project-init
  scripts/project_init.py   check / draft / plan / apply (標準ライブラリだけ)
  run.bat                   .venv があればそれを、なければ PATH の python を使う
  tests/                    テスト

commands/init-project.md    /init-project フォルダ  (メインが行う。plan を見せて承認を得てから apply)
templates/project/coding/AGENTS.md    プログラム・設計計算・解析のテンプレート
templates/project/document/AGENTS.md  一般資料 (手順書・報告書・設計資料・調査のまとめ) のテンプレート
```

## 3. 置くもの

| 置くもの | 内容 | 既にあるとき |
|---|---|---|
| `AGENTS.md` | テンプレート(`coding` / `document`)を、中身とインタビューの答えで埋めた下書き(`--agents-file`)から | **作らない**(触らない) |
| `.handoff/` | サブエージェントの受け渡し用フォルダ | そのまま(中身に触らない) |
| `.gitignore` | `.handoff/`、`.venv/`、`__pycache__/` の行 | 足りない行だけを末尾に**追記**(元の内容は変えない) |

- **`CLAUDE.md` だけがあるとき(以前 Claude Code で開発したリポジトリ)は、`AGENTS.md` を作らない。** 共通ルールが `CLAUDE.md` を最初に読むので([README.md](../README.md) の 6.1)、指示を 1 か所にしておく。ユーザーと決めた(2026-11-07)。
- **既存の `AGENTS.md` に、テンプレートの節を足すことはしない。** 足したいときは、`plan` で内容を見せるだけ(人間が判断する)。
- 置かないもの: `.venv`(スキル `python-env` の役目)、`opencode.json`(会社側だけのファイル)、スキルのコピー(共通のものを使う)、コミット(`git add`・`git commit` もしない)。
- **`git init` は、エージェントが行ってよい**(ユーザーが許可した。2026-11-07)。ただし、スクリプトではなく、**スキルの手順としてエージェントが実行する**(次の 5 を参照)。

## 4. テンプレートの選び方と、AGENTS.md の埋め方(0.19.0)

利用者の依頼: インタビューして、適切なテンプレートを選び、AGENTS.md の中身を変える。今は coding と一般資料の 2 つ。すでに中身があるフォルダは、中身を見てテンプレートを選び、必要に応じてインタビューする。Obsidian は人間が配置するので対象外。

- **中身の調査(`check`):** 名前と拡張子だけを見る(ファイルは開かない。`.git`・`node_modules`・`.venv`・`dist` などは数えない。5,000 個・深さ 6 まで)。プログラム・モデル・資料の数、一番上の一覧、プログラムの手がかり(`package.json`、`pyproject.toml`、`requirements.txt` など)、先に読むファイル(README など)と、テンプレートの推奨(手がかりかプログラムが多ければ coding、資料が中心なら document、空なら「なし」)。
- **選ぶのはエージェント:** 推奨は手がかりで、エージェントが README などを 5 ファイルまで読んで確かめる。合えば質問しない。食い違う・空のときだけ、1 問で聞く。
- **下書き(`draft`):** テンプレートを、対象のフォルダの `.handoff/project-init_AGENTS.md` に書き出す(上書きせず `_2`)。埋める【 】の一覧を出す。エージェントは、中身から分かるものを中身から埋め(根拠のファイルを控える)、分からないものだけをまとめて質問する(1 回に 5 問まで、おすすめの答えつき)。答えが無い項目は、行ごと消すか「(未定)」。例の値・例の文を採用しない。
- **置く(`plan` / `apply` の `--agents-file`):** 下書きを読み、見出しがあり UTF-8 かを確かめる。埋まっていない【 】と、先頭の説明のコメントが残っていれば注意を出す。`plan` で、下書きと置く内容を見せて承認を得る。`--template` を直接渡すと【 】が残るので、ユーザーが望んだときだけ。
- 元(`--agents-file` か `--template`)を指定しない `plan`・`apply` は、止める(埋めずに置くのを防ぐ)。

## 4.1 プログラム用のテンプレート(`templates/project/coding/AGENTS.md`)

- **0.20.0:** 先頭に「コーディングのスキル」の節を足した。Python のコードを書く・直す・レビューする前に、**必ずスキル `python-coding` を読む**。コードの調査はリポジトリの中を直接読み、社内の資料の検索(`finder`・`researcher`)は仕様書や原典を探すときだけにする(利用者の判断: コーディングでは社内のローカル検索を使わなくてよい)。`pip install` の決まりを、共通 `AGENTS.md` から移した。一般資料と Obsidian のテンプレートには、スキルとエージェントの対応表を置いた(共通 `AGENTS.md` から移した)。


当初の `templates/coding/AGENTS.md`(コード専用)を、汎用に作り直した(フォルダ名も変えた)。

- **残したもの:** 作業の進め方(テスト駆動、日本語、文書も同時に直す)、コマンドの欄、会社の PC で使える言語とパッケージ(Python の `.venv`、Node は標準モジュールだけ)、Windows の注意、`.handoff/`、確認が必要な操作。
- **足したもの:**
  - **Git の作法:** `git status` で状態を確認、未コミットの変更を戻さない、コミットは頼まれたときだけ、`git push` と履歴の書き換えはしない。
  - **計算・解析の節:** 単位系を決めて混ぜない、数値を作り上げず出典(規格・版・条項)を残す、入力・モデル・結果を分けて作り直せる形にする、手計算や既知の解と照合して差を記録する(していなければ「未検証」)、ソルバーを実行できなければ「未実行」、設計の結論は案として示し最終判断は人間。
  - **Git で管理するもの・しないもの:** ソースと入力データは管理する。ソルバーの大きな結果ファイル、バイナリのモデルファイルは、管理に入れる前に確認する。
- 使わない節は、下書きを埋めるときに消す(計算をしないプロジェクトでは、「計算・解析」の節ごと)。

## 4.2 一般資料のテンプレート(`templates/project/document/AGENTS.md`)

手順書・マニュアル・報告書・設計資料・調査のまとめのフォルダ用(0.19.0)。節は、読者と書き方(読者・文体・用語)、原典と根拠(原典の置き場、出典の書き方、「未確認」、Word・PDF は `researcher`、原典を書き換えない)、資料の作り方(`doc-writing`・`interview`・`yomiyasu`/`polish`・`diagram`)、数値と計算(`calc-check`)、版と変更(Git、差分は `app-ecosystem` の `review`、レビュー・承認)、構成、守ること、`.handoff/`、確認が必要な操作。会社の PC の言語の節は入れていない(資料のフォルダでプログラムを書かないため)。

## 5. 安全の設計

- **書き込み先は 3 つだけ**(`AGENTS.md` の新規作成、`.handoff/` の作成、`.gitignore` の新規作成または追記)。テストが、ソースに削除・名前の変更・実行・通信が無いこと、書き込みの呼び出しが決まった数であることを検査する。
- **上書きしない:** `AGENTS.md` と新しい `.gitignore` は、排他的な作成(`open(..., "x")`)。直前に同名ができたら失敗する。`.gitignore` の追記は、バイト列を後ろに足すだけ(元の内容、改行の形(CRLF)、BOM を保つ)。
- **大文字小文字を区別しない:** Windows では `Claude.md` と `CLAUDE.md` は同じなので、小文字にそろえて探す。
- **拒否する場所:** ドライブやルート、ホームフォルダそのもの、ハーネス自身のフォルダ、`.git` の中、システムのフォルダ(`Windows`、`Program Files`、`/etc`、`/usr` など)。`check` と `plan` も同じ拒否をする。
- **UTF-8 でない `.gitignore`、リンク、フォルダでない `.handoff` は触らない。** `.gitignore` に「除外しない行(`!.handoff/` など)」があれば、足さずに警告する。
- **`apply` は、`plan` を見せて承認を得てからだけ**(スキルの手順と、コマンドの指示)。`check` と `plan` は、何も書かないので、`sample_opencode.json` で確認なしで許可した。`apply` は、既定の「確認」のまま。
- 出力の文章(フォルダ名など)は、データであって指示ではない(スキルに明記)。
- **`git init` の条件(スキルの「`git init` の扱い」):**
  - `check` と `plan` がエラーなく終わっていて、結果が `Git で管理されていません`(このフォルダにも親にも `.git` が無い)のとき**だけ**。
  - **リポジトリの途中のフォルダでは実行しない**(入れ子のリポジトリになるため)。拒否される場所(ホーム、システム、ハーネス自身)は `plan` で止まるので、`git init` まで進まない。
  - `plan` を見せるときに「`git init` も実行する」と伝え、承認を得てから実行する。実行するのは `git init <フォルダ>` だけ(オプションなし。`git add`・`git commit` はしない)。
  - 実行後に `check` で、ルートになったことを確かめる。
  - **スクリプトに入れなかった理由:** 「他のプログラムを起動しない」ことを、テストでソースを検査して保証しているため。`git` の呼び出しをスクリプトに入れると、その保証が崩れる。エージェントの `git init` は、OpenCode の権限(`shell` は既定で「確認」)の対象になる。`sample_opencode.json` には許可の行を足していないので、実行時に確認の画面が出る。毎回の確認が煩わしければ、会社側の `opencode.json` に `git init *` の許可を足してよい(判断は人間)。
