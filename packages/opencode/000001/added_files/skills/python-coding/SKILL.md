# Python のコーディング

公開されている Python のスキル(下の「参考」)の共通点を、会社の環境(オフライン、Windows、`.venv` と pip、社内の小さいモデル)に合わせてまとめたもの。プロジェクトの `AGENTS.md` と食い違うときは、プロジェクトに従う。

## 進め方

1. **読む。** `README.md`、`pyproject.toml` / `requirements*.txt`、変える所の周りのコードとテストを読む。既存の書き方(名前、構成、テストの形)に合わせる。
2. **テストを先に書く。** 新しい機能や不具合の修正は、先にテストを書き、**失敗することを実行して確かめてから**実装する。テストが通ったら、動作を変えずに整える。
3. **小さく変える。** 1 つの変更で 1 つのこと。依頼の外のリファクタリング・整形・名前の変更はしない。
4. **確かめる。** 下の「確かめる」を実行する。実行できなかったものは「未実行」と報告する。

## 書き方

- **標準ライブラリを先に使う。** パッケージを足すのは、標準ライブラリでは無理なときだけ。足す前にユーザーに確認し、バージョンを固定して `requirements` に書く(手順はスキル `python-env`)。
- **型ヒントを、すべての関数の引数と戻り値に付ける。** `list[str]`、`dict[str, float]`、`X | None` の形(3.10 以降。古い Python なら `from __future__ import annotations`)。`Any` は避ける。まとまったデータは `dataclass` にする。
- **関数は小さく、1 つの仕事。** 計算(入力から値を返すだけ)と、入出力(ファイル、画面、ネットワーク)を分ける。計算の関数はテストしやすくする。グローバルな状態を書き換えない。
- **名前:** 関数・変数は `snake_case`、クラスは `CapWords`、定数は `UPPER_CASE`。**単位は名前かコメントに書く**(`length_mm`、`force_n`)。
- **docstring とコメントは日本語。** 関数の docstring に、何を受け取り何を返すか、単位、出す例外を書く。コメントは「なぜ」を書く(「何をしているか」はコードで分かるようにする)。
- **例外:** 具体的な例外型を出し、具体的な型で受ける。`except:` と `except Exception: pass`(握りつぶし)は使わない。入力は早めに検査し、何が悪いかが分かる言葉で `raise` する。
- **ログと出力:** 調べるための出力は `logging`。`print` は、CLI の結果を出すときだけ。
- **ファイル:** パスは `pathlib.Path`。`open()`・`read_text()`・`write_text()` には **必ず `encoding="utf-8"` を付ける**(Windows の既定は cp932 で、文字化けや失敗の元になる)。`with` で開く。大事なファイルを上書きする処理は、一時ファイルに書いてから置き換えるか、先に確認する。
- **パスを決め打ちしない。** フォルダは引数か設定で受け取る。区切り文字を文字列で組み立てない(`Path` の `/` を使う)。
- **外部コマンド:** `subprocess.run([...], check=True, timeout=…)` の形。`shell=True` は使わない。
- **数値:** 浮動小数点の比較は `math.isclose`(テストは `pytest.approx`)。お金や桁を厳密に扱う値は `decimal.Decimal`。換算の係数は、名前を付けた定数にして出典を書く。
- **コマンドライン:** `argparse` と `if __name__ == "__main__":`。パッケージの中は `python -m パッケージ.モジュール` で実行する。
- **秘密:** パスワード・API キーをコードやテストに書かない。`.env` を Git に入れない。

## テスト

- 置き場所は `tests/test_*.py`。`pytest` が入っていれば `pytest`、無ければ標準の `unittest`(プロジェクトに合わせる)。
- 1 つのテストで 1 つの振る舞い。名前で何を確かめるかが分かるようにする(日本語の名前でもよい)。
- 正常な値だけでなく、境界の値(0、空、最大)と、誤った入力(例外が出ること)も確かめる。
- ファイルを使うテストは、一時フォルダ(`tmp_path`、`tempfile`)の中だけで行う。ネットワーク・本番のデータ・ユーザーのフォルダに触れない。
- 計算のテストの期待値は、手計算・既知の解・規格の例から取り、テストに出典を書く。実装を動かした結果を、そのまま期待値にしない。
- テストを通すために、テストを消す・弱める・`skip` することはしない(必要なら理由を示して確認する)。

## 確かめる

```
.venv\Scripts\python -m pytest            (Mac は .venv/bin/python。無ければ -m unittest discover -s tests)
.venv\Scripts\python -m ruff check .      (入っているときだけ)
.venv\Scripts\python -m mypy .            (入っているときだけ)
.venv\Scripts\python -m compileall -q .   (ruff・mypy が無いときの最低限の構文チェック)
```

- プロジェクトの `AGENTS.md` にコマンドがあれば、それを使う。
- `uv` は、プロジェクトで使っているときだけ使う(会社の PC に入っているとは限らない)。
- 失敗を `# type: ignore` や `# noqa` で隠さない(どうしても要るときは、理由をコメントに書く)。

## しないこと

- 依頼の外のファイルの変更、ついでの整形。
- lint を通すために、使われている公開の関数・引数を消す。
- 動いているかを確かめずに「直りました」と報告する。
