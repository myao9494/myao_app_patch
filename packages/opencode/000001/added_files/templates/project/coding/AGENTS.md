## コーディングのスキル

- **Python のコードを書く・直す・レビューする前に、必ずスキル `python-coding` を読み込む**(`skill` の道具。プロジェクトの中に無ければ、`~/.config/opencode/skills/` にある)。
- コードの調査は、リポジトリの中を直接読む(read・grep・glob)。社内の資料の検索(`finder`・`researcher`)は、仕様書や原典の資料を探すときだけ使う。
- 仮想環境とパッケージの追加は、スキル `python-env`。

## 作業の進め方

- 作業を始める前に、`README.md` と `docs/` の関係する文書を読む。
- 変更の前に、`git status` で状態を確認する。未コミットの変更は、勝手に戻さない・消さない。
- コミットは、頼まれたときだけ行う。`git push` と、履歴の書き換え(`reset --hard`、`rebase` など)はしない。
- プログラムの新しい機能や不具合の修正は、テストを先に書く(テスト駆動)。先に失敗することを確認してから、実装する。
- 各ファイルの冒頭と主要な関数の前には、日本語のコメントで仕様(何を入力して、何を返すか。単位も)を書く。
- コード、ドキュメント、画面の文言は日本語で書く。
- 動作や計算の中身を変えたら、関係する `docs/` の文書も、同じ変更の中で直す。コードと文書が食い違っていたら、どちらかに勝手に合わせず、報告して確認する。
- 既存の書き方と構成に合わせる。新しいライブラリは、先に確認してから追加する。

## 計算・解析(設計計算、構造計算、CAE など)

- 単位系を決めて、この節か `docs/` に書く(【例: N、mm、MPa】)。違う単位を混ぜない。変数名かコメントに、単位を書く。
- 数値(材料定数、許容値、荷重、規格の値)を、作り上げない。出典(規格・文献・社内基準の名前、版、条項、ページ)を、入力データか文書に残す。出典が分からないものは「未確認」と書く。
- 入力(条件・パラメータ)、モデル、結果を分けて保存する。結果は、入力とスクリプトから作り直せる形にする。手で書き換えた結果を、そのまま置かない。
- 結果は、手計算、既知の解、過去の結果のどれかと照合して、差を記録する。照合していない結果は「未検証」と書く。
- 解析ソフト(ソルバー)は、この PC で実行できないことがある。実行して確かめられなかった解析や結果は、「未実行」と書く。
- 設計の結論(合否、安全率、採用する寸法)は、案として示す。最終の判断は人間が行う。

## Git で管理するもの・しないもの

- 管理する: ソースコード、入力データ(条件・パラメータ)、モデルを作るスクリプト、`docs/`、`requirements` のファイル、小さな基準の結果。
- 管理しない: `.venv/`、`.handoff/`、ソルバーが出す大きな結果ファイルや一時ファイル(【拡張子を書く】)。決まったら `.gitignore` に入れる。
- バイナリのモデルファイル(【例: CAE のモデル】)は、差分が見えない。大きいものを Git に入れる前に、確認する。変更したら、何を変えたかを `docs/` か変更履歴に書く。

## 会社の PC で使える言語とパッケージ

- Python は使える。`pip install` でパッケージを追加できる。標準ライブラリで足りるなら、標準ライブラリを使う。`pip install` は、`requirements` にあるか、ユーザーが名前を指定したパッケージだけを、バージョンを指定して入れる。追加したパッケージは、`requirements.in` などに記録する。
- Python は、プロジェクト直下の `.venv/` を使う。なければ `python -m venv .venv` で作る。実行は `.venv\Scripts\python`(Windows)、`.venv/bin/python`(Mac)の形で指定する。`pip install` も、venv の中に入れる。本体の Python には入れない。`.venv/` は `.gitignore` に入れる。
- Node.js は入っているが、`npm install` や `npx` でパッケージを取得できない。会社の PC では、Node.js は標準モジュールだけで動くスクリプトに使う(構文チェックは `node --check`、テストは `node --test`)。
- フロントエンドのビルドや、`node_modules` が必要なテストは、自宅で行う。ビルド済みの成果物(`dist/` など)を Git で管理して、会社へ運ぶ。会社の PC で `npm install` を試さない。
- 会社の PC で実行できなかったテストやビルドは、報告に「実行できなかった」と書く。

## Windows の会社 PC で動かすもの

- `.bat` ファイルには、日本語を書かない(ASCII だけにする)。会社の PC では、行が誤って解釈されることがある。
- パスは、大文字と小文字を区別しない前提で書く。名前の大文字小文字だけが違うファイルを、同じフォルダに作らない。
- Windows でしか動かない部分は、Mac では実行して確認できない。変更したら、確認できていないことを報告に明記する。
