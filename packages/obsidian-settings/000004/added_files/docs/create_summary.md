# 仕様書: 複数マークダウンファイルのサマリー（統合）作成機能

## 概要
Obsidian上で開いているマークダウンファイル（通常の `.md` ファイル）を起点とし、そのファイルおよびリンク先のマークダウンファイルを指定した最大深さまで再帰的に収集して1枚のマークダウンファイルに統合（サマリー作成）します。
生成されたサマリーファイルは `10_summary` フォルダ配下に保存され、自動的に新しいタブで開かれます。

## トリガー
- マークダウンファイルのタブやファイルエクスプローラー内での右クリックメニュー（`file-menu`）および、エディタ内で右クリックしたときのメニュー（`editor-menu`）から「サマリーを作成」を選択。
- 通常の `.md` ファイルのみが対象（`.excalidraw.md` は除外されます）。

## 詳細動作仕様
1. **最大深さの指定と収集**:
   - 実行時、最大深さの指定ダイアログ（デフォルト: 2）を表示して入力を求める。
     - Obsidian の `Modal` および `Setting` クラスが取得できる環境（通常環境）では、自動フォーカスとテキスト全選択が効いたカスタムダイアログ（`SummaryDepthModal`）を使用する。
       - ダイアログ内の入力要素は数値入力用（`type="number"`, `min="0"`）とし、Windowsおよびモバイル環境での動作の安定性を確保する。
       - タイミングによるフォーカスの競合を防ぐため、ダイアログの自動フォーカスおよびテキスト全選択処理はモーダルの `onOpen` ライフサイクルメソッド内で実行する。
     - `Modal`/`Setting` クラスが取得できない環境（モバイル版やプラグインロード順の影響など）では、Templaterの `tp.system.prompt` を使用して入力を求める。
     - いずれも利用できない、もしくはエラーが発生した場合はデフォルトの深さ `2` を使用して処理を続行する。
     - ユーザーがキャンセル（カスタムダイアログでのキャンセルまたは `tp.system.prompt` でのキャンセル）した場合は処理を中断する。
   - 起点ファイルから `links`（通常の `[[リンク]]`）および `embeds`（埋め込み `![[リンク]]`）を解析。
   - 指定された最大深さ（`maxDepth`）まで再帰的に収集する。
     - 深さ0: 起点ファイル
     - 深さ1: 起点ファイルから直接リンクされているファイル
     - 深さ2: 深さ1のファイルからさらにリンクされているファイル
   - 各ファイルの拡張子が `.md` であり、かつ `.excalidraw.md` でないもののみを収集対象とします。
   - 解決できないリンクや非マークダウンファイルは安全にスキップされます。

2. **重複制御（循環参照への対応）**:
   - A -> B -> A のような循環リンクや、複数ルートから同一ファイルへリンクされている場合でも、同一ファイルを2回以上収集しないよう重複制御（パスを用いたSetによる管理）を行います。これにより無限ループを防止します。

3. **統合フォーマット**:
   - 生成されるサマリーファイルの最上部に、ダイアログで選択された共通プロンプトファイル（`11_common_prompt` フォルダ配下の Markdown ファイル。`common_prompt.md` はデフォルトで ON、他は OFF。デフォルトの `common_prompt.md` には、AIが出力時に画像・図の元のObsidianリンクを正確に復元してMarkdown出力するための指示が記述されています）の内容が、それぞれ `# Source: 11_common_prompt/{ファイル名}` ヘッダー付きで挿入され、`\n---\n` で区切られます。メンションタグ（`@[...]`）は出力しません。なお、`common_prompt.md` が選択されている場合は、他のファイルより先に、常に一番上（最優先）に配置されます。
   - 収集された各ファイルは、以下の区切りフォーマットを用いて結合されます。
     ```markdown
     # Source: {Vault内相対パス}
     {ファイルの内容}
     ```
   - 各ファイル間は `\n---\n`（水平線）で結合されます。

 3.5. **画像・Excalidrawの相対パス・プレビュー変換と元のリンク併記**:
   - サマリー内に統合される各マークダウン中のObsidian形式画像埋め込み（`![[画像]]` や `![[画像|幅]]`）や通常リンク（`[[画像]]` や `[[画像|表示名]]`）は、サマリーファイル（`10_summary/`）から見た相対パス（`../[Vault内パス]`）に置換されます。この際、元の埋め込みで指定されていた画像サイズ（例：`|400` などの幅指定）が存在する場合、プレビューやPDF等で確実にサイズ制限が機能するように、標準マークダウン形式ではなく HTML の `<img src="path" width="幅">` 形式で出力されます。サイズ指定がない場合は、通常のマークダウン画像記法（`![](path)`）として出力されます。
   - 置換された画像・リンク（HTMLタグ等）のすぐ直後には、元のObsidianリンクがObsidian上で画像として再レンダリングされるのを防ぐためにバッククォートで囲み、さらにPDF出力（レンダリング）時に画像の下にテキストが隠れてしまわないように `<div>` 要素で囲んだブロック形式（例: `<div>[元のリンク: `![[image.png|400]]` ]</div>`）で直接出力されます。これにより、画面に画像が2重に描画されたりPDF出力時にテキストが消えたりするのを防止しつつ、会社のAIがPDFを読み込んだ際に元のリンク情報を確実に認識・復元できるようになります。
   - `.excalidraw.md` ファイルに対する埋め込み・リンクについては、自作プラグイン `obsidian-excalidraw-cards` が自動生成するキャッシュ用フォルダである `.excalidraw-cache` 配下のプレビュー画像ファイル（`[filePathのFNV-1aハッシュ]_[mtime].png`）を自動的に特定し、その画像への相対パスへと置換します。この場合もサイズ指定があれば `<img src="excalidraw-cache/..." width="幅">` 形式で出力されます。
   - キャッシュ画像ファイルを `10_summary/excalidraw-cache/` 配下にコピーする際、WindowsなどのOS特有のパス解釈の違いによるコピー失敗を避けるため、Node.jsの `fs` および `path` モジュールが利用可能な環境（デスクトップ環境など）では `fs.copyFileSync` を使用した絶対パスでのファイルコピーを優先します。Node.jsが利用できない環境では `app.vault.adapter.copy` による従来のコピー処理へフォールバックします。
   - これにより、VSCodeやObsidian等の各種マークダウンプレビューやPDFエクスポートにおいて、図や画像が正常かつ意図したサイズでレンダリングされます。なお、Obsidian内のCSSスニペット `excalidraw-embed-width.css` によって `img[src*="excalidraw"]` などの幅が `100% !important` に強制されサイズ指定が無視される競合問題については、同CSS内のセレクタに `:not([width])` を追加することで、HTMLの `width` 属性によるサイズ指定を正しく機能させて回避しています。

4. **保存と事後動作**:
   - Vaultのルート配下に `10_summary` フォルダが存在しない場合は自動作成します。
   - ファイル名は `10_summary/[元のファイル名]_summary.md` となります。
   - 同名のサマリーファイルがすでに存在する場合は上書き（`modify`）され、存在しない場合は新規作成（`create`）されます。
   - 作成後、「サマリーを作成しました」という Notice が表示され、生成されたサマリーファイルが自動的に新しいタブで開かれます。
   - サマリー作成後、同じ内容のAIコンテキスト用HTMLが保存ダイアログなしで `10_summary/[元のファイル名]_summary.html` に自動保存されます。

5. **APPENDIX（メール添付ファイル）の自動結合**:
   - 探索されたファイルからリンクまたは埋め込まれている `.msg`（Outlookメッセージ）ファイルを検出した場合、サマリーファイルの末尾に `## APPENDIX: メール添付ファイル` セクションを自動的に追加します。
   - Outlookのインストールを前提としないため、ピュアJSによる OLE2 (CFB) バイナリパーサーを実装し、直接データを解析・抽出します。
   - 解析対象の情報：
     - **件名**: `Subject` (プロパティ `0037`)
     - **送信者**: `SenderName` (プロパティ `0C1A`)
     - **送信日時**: `SentOn` (プロパティ `0039` = PR_CLIENT_SUBMIT_TIME を優先、フォールバック: `0E06` = PR_MESSAGE_DELIVERY_TIME。通常、OutlookのMSGファイル内ではこれら8バイト値は個別ファイルではなく `__properties_version1.0` ストリームにインラインで格納されるため、同ストリームから直接解析します。FILETIME 8バイト値から UTC 基準で解析し `YYYY-MM-DD HH:mm:ss` 形式で表示)
     - **本文**: `Body` (プロパティ `1000`)。
       - プレーンテキストの本文が存在し、埋め込み画像がない場合は、タグの誤爆や文字化けを防ぐため、整ったプレーンテキスト（`parsed.Body`）を最優先でサマリーに採用します。
       - 埋め込み画像を含む場合、またはプレーンテキスト本文が存在しない場合はHTML本文（プロパティ `1013` = `PR_HTML`）を解析します。
       - HTML本文をテキスト/Markdown化する際は、`sanitizeOutlookHtml` により Outlook/Office 特有のメタデータ・コメント（`<!--[if ...]>...<![endif]-->`、`<xml>...</xml>`、`<o:p>...</o:p>`、`<head>`、`<style>`、MSOクラス等）を完全除去し、「`< >`」タグの残骸や文字化けがサマリー内に露出するのを確実に防止します。
       - メール本文中の山括弧は安全にエスケープされ、Obsidian上での意図しないHTML再実行を防ぎます。
   - デコード時の文字コード対応：
     - UTF-16LE 形式 (`001F` 系のストリーム) だけでなく、Windows のクラシック Outlook からドラッグ＆ドロップされた Shift-JIS / CP932 形式 (`001E` 系のストリーム) の ANSI 文字列、さらには HTML 本文などに用いられる `PT_BINARY` 形式 (`0102` 系のストリーム。主に `PR_HTML` 向け) も文字化けなく正常に復号します。
     - `PT_BINARY` ストリームのデコード時は、まず UTF-8 で仮デコードして HTML 内の `charset` 設定（例: `charset=utf-8` や `charset=shift_jis`）を検出し、指定されたエンコーディングがある場合は `TextDecoder` で再デコードします。
     - グローバルの `TextDecoder` を直接使用し、`require("util")` には依存しません。
   - 出力形式：
     - メール本文は4バッククォート（```` ````）のコードフェンスで囲み、本文中に ``` が含まれる場合でもマークダウン構造が壊れないようにします。
   - 安全なフォールバック設計：
     - OLE2 構造の破損やその他非対応フォーマットなどのエラーが発生した場合でも、全体のサマリー作成処理を中断させず、当該ファイル箇所に「ファイルの解析に失敗したか、動作環境が非対応です」というフォールバックメッセージを記載した上で、安全に処理を続行します。

## 設計構造

```
[起点ファイル (Depth 0)]
   │
   ├─► [リンク先A (Depth 1)] ──► [リンク先C (Depth 2)] ──► [Depth 3 (収集対象外)]
   │
   └─► [リンク先B (Depth 1)]
```

収集されたファイルコンテンツは、探索順（Depth 0 -> Depth 1 -> Depth 2 ...）に結合され、サマリーファイルとして出力されます。
